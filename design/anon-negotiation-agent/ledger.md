### I-1（実装時の気づき / 設計 / low）§2.4 の性質の 2 文目「外しても交渉ができなくなることはない」は、条件付きでしか成り立たない

  - 候補者側の AI は受けられる案しか出せない（ガード）ので、何も提案できない。

- **扱いの時期**: 面談を作る段で、ほかの実装時の気づきとまとめて設計書を直し、承認し直す（ユーザーの判断、2026-09-29）。① と ② の実装には影響しない。
- **扱いの案**（面談を作る段で決める。設計書の変更なので承認のし直しが要る）

### I-2（実装時の気づき / 設計 / medium）本物の候補者の属性帯を、どこに持つかが書かれていない

- **根拠**: 1b-1 の実装で見つかった。§3.1 の `participants` と §2.7 の `counterparty` は候補者の属性帯を使う。§3.1 の `snapshots` では、求人側のルールに帯を当てはめる。しかし、帯をどこに保存し、交渉の作成時にどこから取るかが、§3.3・§3.8・§5 のどこにもない。§3.8 の `principals/{pid}` の項目にも入っていない。
- **破綻シナリオ**: 1b-1 は、交渉の作成のたびに web から帯を受け取る形で実装した。この形では、交渉ごとに違う帯を渡せる。そうすると、求人側の帯ごとのルール（例: 経験 5〜10 年なら上限 750 万）を、帯を変えながら探れてしまう。あわせて、web が帯をどこに持つかも未定のまま残る。
- **決定**（ユーザーの判断、2026-09-29）: 面談の送信（§5 の手順 9）で、帯をポリシーと一緒に金庫の `principals/{pid}` に保存する。交渉の作成時は、金庫がそこから読み、作成の要求では受け取らない。1b-1 の差し戻しで実装する。
- **設計書の直し**: §3.3 の policy の PUT、§3.8 の保存項目、§5 の手順 9 に帯を足す。I-1 とまとめて、面談の段で承認し直す。

### I-3（実装時の気づき / 設計 / low）「24 時間の評価予算」の数え方が書かれていない

- **根拠**: 1b-1 の実装で見つかった。§3.5 は「本物の依頼者ごとの 24 時間の評価予算: 160」とだけ書く。固定の窓（最初の予約から 24 時間ごとに 0 に戻す）か、直近 24 時間か、が決まっていない。
- **決定**（ユーザーの判断、2026-09-29）: 固定の窓（1b-1 の実装のまま）。
  - 窓の切り替わりの前後で、短い間に最大 2 倍（交渉 20 件分）使える。

- **設計書の直し**: §3.5 に固定の窓と書く。I-1 とまとめて、面談の段で承認し直す。

### I-4（実装時の気づき / 設計 / low）削除と、途中にある同じ依頼者の書き込みが競合すると、金庫に依頼者の文書が作り直される

- **根拠**: 1b-2 の差し戻しで、金庫の各操作に「削除中なら拒否」を入れた。
  - 交渉の作成は、トランザクションの中で確かめるので、競合しても必ず正しく解決される。
  - policy・blocklist の PUT は「確かめてから書く」の 2 手で、トランザクションではない。
- **破綻シナリオ**
  1. web が PUT policy を金庫に送る。
  2. それが届く前に、本人の削除が金庫の手順 1〜4 を最後まで済ませる（交渉がなければ一瞬で済む）。
  3. 遅れて届いた PUT が、依頼者の文書を作り直す。
  4. 墓標がない（C-20）ので、金庫は「新しい依頼者」と区別できない。web の `principals_meta` はすでに消えているので、見回りもこの文書を拾わず、残り続ける。
- **扱い**: 1d（web）で、同じ依頼者の操作と削除の流れを 1 つずつ順に処理する。
  - web は 1 インスタンス（§1.1）なので、プロセスの中の依頼者ごとのロックで足りる。
  - 削除の流れは、印を立てる前にロックを取り、最後まで持つ。途中にある操作が終わるのを待ってから削除する。
  - 30 日の自動削除も、同じロックを使う。
  - 設計書の意味（§6.3「以後、その依頼者の操作はすべて拒否する」）を変えずに、その実現方法を決めるものなので、設計書の直しは I-1 とまとめるときに 1 行足すだけにする。
  - 1d-1 の申し送り: 見回りの `stages/{nid}` の作成と、レフェリーの操作も、同じ種類の競合を起こし得る。依頼者ごとのロックの対象に入れる。

### I-6（実装時の気づき / 設計 / low）デモ・攻撃の交渉の段の状態 `stages/{nid}` を消す経路がない

- **根拠**: 1d-1 の報告。
  - 見回りは、架空の候補者の交渉にも、段 0 の `stages/{nid}` を作る。
  - 金庫のデモ・攻撃の交渉には TTL（96 時間）がある。一方、web の `stages/{nid}` には、TTL も削除もない（§3.8・§6.2）。
- **破綻シナリオ**: デモと攻撃モードを使うたびに、`(default)` に文書が増え続ける。個人情報は含まないが、減ることがない。
- **決定**（ユーザーの判断、2026-09-29）: デモ・攻撃の `stages/{nid}` にも、金庫と同じ 96 時間の TTL を付ける。1d-2 で作る。本物の利用者の段の状態は、これまでどおり本人の削除と 30 日の自動削除で消える。
- **設計書の直し**: §3.8・§6.2 に 1 行足す。I-1 とまとめる。

### I-7（実装時の気づき / 設計 / medium）本番で必須の設定（調査事項 R-2 の結果）と、R-1・R-3 の途中結果

- **R-2 の結果**
  - ADK は、既定でトレースにメッセージの内容を取り込む。本番では `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` が必須。対象は面談だけでなく、交渉エージェントも含む。
  - a2a-sdk と ADK は、DEBUG のログにリクエストの本文を出す。本番のログは INFO 以上にする。
  - どちらも AC-02・AC-18（カナリアがどこにも残らない）に直結する。
- **R-1 の結論**: ADK の `to_a2a` は使わず、受信口ごとの自前の AgentExecutor にした（1c）。`to_a2a` では、次のことが起きるため。
  - 検証違反が、A2A のエラーにならない。
  - セッションが、手番をまたいで残り得る。
  - TextPart も LLM に渡る。
  - `Move` が DataPart で返らない。
- **R-3 の途中結果**: pydantic の JSON Schema のままだと、google-genai が整数の列挙値を拒否する。
  - 数値軸は `type=INTEGER, format=enum, enum=[文字列]` に直した（1c）。
  - Vertex AI の実機で通るかは未確認。② の DV-15 で確かめる。
- **扱い**: デプロイの段の確認項目に入れる。設計書の §10・§15 の直しは、I-1 とまとめる。
- **追記（1d-2 の報告、2026-09-30）**: デプロイの確認項目に、次を足す。
  - web は uvicorn を workers=1 で動かす。依頼者ごとのロック（I-4）は、プロセスの中の asyncio のロックなので、複数のプロセスでは保証が崩れる。
  - Firestore の TTL ポリシーを、web の `stages` の `ttl_at`（I-6）と、金庫のデモ・攻撃の交渉と、各イベントの記録の期限の項目に設定する。
  - web の必須の環境変数は `SESSION_SIGNING_KEY`（Secret Manager から渡す）と `VAULT_BASE_URL`。
  - サービス間の認証（Cloud Run の ID トークン）は、まだない。

- **追記（fix-2 の報告、2026-10-02）**: トークンが使えないとき（宛先違い・取得の失敗）、レフェリーはログを残さずに待つ。運用で気づきにくいので、ログを足すかを、デプロイの段でユーザーに確かめる。

### I-9（実装時の気づき / 前提 / low。デプロイの段でユーザーの判断を待つ）Cloud Run 自身のリクエストログに、ID の入った URL が残る

### I-13（実装時の気づき / 実装 / medium）DV-15（本物の Gemini でケース 1）の経過と、R-3 の結果

- 2026-10-02、プロジェクト `anon-nego-toshixa`・`gemini-3.5-flash`・global・temperature 0 で、`scripts/run_demo.py --case 1 --live` を実行した。

  2. **2 回目: 不合格**。無効手は 0 件（構造化出力の列挙値の制約は効く。R-3 の確認）。ただし、双方が手数 6 を使い切り `stopped_budget`。

     - 求人は当直を最後まで 8 回のままにした。
     - 双方とも、指示文の「最初から一緒に動かす」を守らず、7 巡目の「年収を先に譲る型」に近い動きになった。

       - 値の違う数値軸は、すべて 1 段ずつ寄せる。
       - 受けられなければ、寄せた軸を 1 つずつ戻して確かめ直す。
       - 差が縮んだら、相手の案を 1 段寄せた案も確かめる。

       - 例を付けた。
  3. **3 回目: 合格**。年収 700・リモート 2・当直 2・見直し 12 で合意（見込み「高」）。
     - 使った量: 候補者は手数 5/6・評価 12/16、求人は手数 4/6・評価 15/16。
     - 無効手 0 件。LLM の呼び出し 29 回（平均 6.4 秒、最長 9.5 秒）。交渉全体で約 3 分。
  4. **4 回目（確認のため、同じ条件）: 合格**。同じ組み合わせ（年収 700・リモート 2・当直 2・見直し 12、見込み「高」）で合意した。
     - たどった道は 3 回目と違う（求人は年収 300 から始めた）。temperature 0 でも、毎回同じではない。
     - 使った量: 候補者は手数 4/6・評価 12/16、求人は手数 4/6・評価 7/16。
     - LLM の呼び出し 23 回のうち 3 回が 429 RESOURCE_EXHAUSTED。レフェリーの再試行で、3 回とも回復した（無効手 0 件）。最長の呼び出しは 40 秒で、交渉全体は約 5 分。
- **DV-15 は合格**（3 回目と 4 回目）。
- **R-3 の結果（追記）**
  - 429 は、新しいプロジェクトで交渉 1 回の中に 3 回出た。再試行で回復する。
  - デモの当日に複数の人が同時に試すと、遅くなるか止まるおそれがある。

  - 429・5xx は、今回は出なかった。
- **残る危うさ**
