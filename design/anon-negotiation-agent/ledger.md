## 未解決

### P-8（前提 / TEE / 2026-10-03。ユーザーの確認待ち。推奨を既定として進める）機密 VM の種類

- 問い: AMD SEV（`n2d-standard-2`）か Intel TDX（`c3-standard-4`）か。
- 推奨: **SEV**。公式の例の構成で、東京の 3 ゾーンで使え、ホスト保守でライブマイグレーションが効く（TDX は再起動）。費用は TDX の約 45%（1 日 約 450 円 対 約 1,000 円）。TDX は隔離が強いが、2026 年にファームウェアの脆弱性告知が 2 件あり、保護の強さの差を主張の根拠にしにくい。
- 影響: 手順 C の VM 作成コマンドと、トークンの `hwmodel`。鍵の条件と web の検証ポリシーは両方を受けるので、コードは変わらない。

### P-9（前提 / TEE / 2026-10-03。ユーザーの確認待ち。推奨を既定として進める）合否のルール

- 問い: 設計書 §9 の「6 点とも通れば実施」を保つか、3 と 6 の縮退を認めるか。
- 推奨: 1・2・4・5 を必須、3・6 は縮退版でも可（画面と説明文に弱い版だと明記）。理由: 3 は公式に手順がない自前方式で、2 日で通らない確率が最も高い。縮退版（VPC 内 + ID トークン + スクリプトでの検証）でも、鍵の解放（2）と呼び出し元の検証（4）が守るものは変わらない。6 の L1・L2 は 10/7 以降の任意。

### P-10（前提 / 公開 / 2026-10-03。ユーザーの確認待ち。推奨を既定として進める）公開の範囲と、GCP のプロジェクト ID

- 問い: リポジトリ全体を公開するか、金庫だけ別リポジトリか。台帳に書いたプロジェクト ID を伏せるか。
- 推奨: 全体を公開。プロジェクト ID は伏せない。attestation トークンの `gce.project_id` に入り、画面に出す JWT から誰でも読めるので、伏せても意味がない。プロジェクト ID は認証情報ではない。伏せるべきもの（鍵・トークン・`.env`）は最初から入れていない。公開前に履歴の秘密の混入を確かめる。金庫だけ別リポジトリにすると、ビルドの流れとダイジェスト↔コミットの対応を作り直すことになる。

### P-11（前提 / 費用 / 2026-10-03。ユーザーの確認待ち）予算アラートの額

- 問い: いまの 3,000 円をいくらにするか（ユーザーがコンソールで変える）。
- 推奨: **20,000 円**（しきい値 50%・90%・100% で通知）。見込み: SEV の VM 約 9,000 円（検証〜審査終了）＋ ディスク・KMS 約 400 円 ＋ Cloud Run・Firestore・Vertex AI（1 交渉 約 15〜22 円。1 日の上限 1,500 回でも最悪 約 2,300 円/日、実際は 1 日数十回）。TDX にするなら 30,000 円。アラートは通知だけで、止めるのは §8.2 の枠。

### P-12（前提 / 依存 / 2026-10-03。ユーザーの承認待ち）`cryptography`・`google-auth` の明示

- 問い: 直接 import するので `pyproject.toml` に明示してよいか（新しいライブラリではない。ルール上の承認が要る）。
- 推奨: 明示する。`cryptography` 50.0.1（Apache-2.0 OR BSD-3-Clause。AES-256-GCM と X.509 の生成。標準ライブラリにはどちらもない。google-auth・Authlib が推移的に使っている）、`google-auth` 2.58.1（Apache-2.0。`google.auth.jwt` で RS256 の検証。自前の JWT 検証は危ない。Firestore のクライアントが推移的に使っている）。研究報告が挙げた `requests` は、STS と KMS を httpx で直接呼ぶ設計にしたので要らない。承認までは `pyproject.toml` を変えず、実装は進める（どちらも uv.lock にあり、テストは動く）。

### P-13（前提 / TEE / 2026-10-03。ユーザーの確認待ち。既定は「記録による抑止」）オーナーの復号を、拒否ポリシーで拒むか

- 背景（C-58）: プロジェクトのオーナーは基本ロールに KMS の復号権を含むので、IAM を変えずに KEK で DEK を復号できる。既定の対処は Cloud KMS の Data Access 監査ログ（復号の主体と時刻が残る）。
- 問い: プロジェクト `anon-nego`（ユーザー作成）は Google Cloud の組織の配下か。配下なら、IAM の拒否ポリシー（`cloudkms.cryptoKeyVersions.useToDecrypt` をダイジェストの principalSet 以外に拒否）で、オーナーの復号を「記録」から「拒否」に強められる（拒否ポリシーの変更も Admin Activity に残る）。`roles/iam.denyAdmin` の付与には組織の管理者が要る。
- 推奨: 組織の配下でなければ既定のまま（説明文に「運営者が復号すれば記録に残る」と書く）。配下なら拒否ポリシーを足す（スパイクの後、10/5 以降）。

### P-14（前提 / 設計 / 2026-10-03。ユーザーの確認待ち。C-64）計画の寛容な読みと AC-04 の両立

- 背景: 計画の出力は `checks` があれば `move`・`package` を捨てて読む（L16-1・X-74・X-79。JSON モードで `move:"check"` などの形違いが計画全体を手がかりのない `schema_invalid` にしないため）。一方、AC-04 は「未定義の項目やグリッド外の値を含むメッセージは、レフェリーでも拒否する」と求める。両方を満たす実装はない。いまの AC-04 の試験は `Plan` 型を直接検証していて、③ の後は空振りになる。
- 案 1（推奨）: 計画の `move`・`package` に限って AC-04 を読み替える。捨てた値はどこにも渡らない（金庫にも、次の `TurnInput` にも）ので、FR-16 の目的（信用できない入力を通さない）は保てる。`checks` 自体と、`checks` が空のときの `move`・`package` は従来どおり拒否。③ で、AC-04 の試験をレフェリーの実際の読み方（`PlanEnvelope` → `Move`）を通す形に直す。
- 案 2: 寛容な読みをやめ、`move` の違反も `schema_invalid` にする。`last_invalid` に生の値を写して手がかりにする。無効手を 1 つ使い、同じ誤りを繰り返すと 3 回で止まる。
- 答えが出るまで、③ の L16-1 の実装は保留（いまの実装は strict なまま）。
