### I-2（実装時の気づき / 設計 / medium）本物の候補者の属性帯を、どこに持つかが書かれていない

- **根拠**: 1b-1 の実装で見つかった。§3.1 の `participants` と §2.7 の `counterparty` は候補者の属性帯を使う。§3.1 の `snapshots` では、求人側のルールに帯を当てはめる。しかし、帯をどこに保存し、交渉の作成時にどこから取るかが、§3.3・§3.8・§5 のどこにもない。§3.8 の `principals/{pid}` の項目にも入っていない。
- **破綻シナリオ**: 1b-1 は、交渉の作成のたびに web から帯を受け取る形で実装した。この形では、交渉ごとに違う帯を渡せる。そうすると、求人側の帯ごとのルール（例: 経験 5〜10 年なら上限 750 万）を、帯を変えながら探れてしまう。あわせて、web が帯をどこに持つかも未定のまま残る。
- **決定**（ユーザーの判断、2026-09-29）: 面談の送信（§5 の手順 9）で、帯をポリシーと一緒に金庫の `principals/{pid}` に保存する。交渉の作成時は、金庫がそこから読み、作成の要求では受け取らない。1b-1 の差し戻しで実装する。
- **設計書の直し**: §3.3 の policy の PUT、§3.8 の保存項目、§5 の手順 9 に帯を足す。I-1 とまとめて、面談の段で承認し直す。

### I-4（実装時の気づき / 設計 / low）削除と、途中にある同じ依頼者の書き込みが競合すると、金庫に依頼者の文書が作り直される

- **根拠**: 1b-2 の差し戻しで、金庫の各操作に「削除中なら拒否」を入れた。
  - 交渉の作成は、トランザクションの中で確かめるので、競合しても必ず正しく解決される。
  - policy・blocklist の PUT は「確かめてから書く」の 2 手で、トランザクションではない。
- **破綻シナリオ**
  1. web が PUT policy を金庫に送る。
  2. それが届く前に、本人の削除が金庫の手順 1〜4 を最後まで済ませる（交渉がなければ一瞬で済む）。
  3. 遅れて届いた PUT が、依頼者の文書を作り直す。
  4. 墓標がない（C-20）ので、金庫は「新しい依頼者」と区別できない。web の `principals_meta` はすでに消えているので、見回りもこの文書を拾わず、残り続ける。
- **扱い**: 1d（web）で、同じ依頼者の操作と削除の流れを 1 つずつ順に処理する。
  - web は 1 インスタンス（§1.1）なので、プロセスの中の依頼者ごとのロックで足りる。
  - 削除の流れは、印を立てる前にロックを取り、最後まで持つ。途中にある操作が終わるのを待ってから削除する。
  - 30 日の自動削除も、同じロックを使う。
  - 設計書の意味（§6.3「以後、その依頼者の操作はすべて拒否する」）を変えずに、その実現方法を決めるものなので、設計書の直しは I-1 とまとめるときに 1 行足すだけにする。
  - 1d-1 の申し送り: 見回りの `stages/{nid}` の作成と、レフェリーの操作も、同じ種類の競合を起こし得る。依頼者ごとのロックの対象に入れる。

### I-5（実装時の気づき / 実装 / low）DV-02 の 10 本の並行テストが、負荷が高いと揺らぐ

- **根拠**: 2026-09-29、1c の worktree でテスト全体を流したときに見つかった。
  - そのとき、別の worktree のテストも同時に走り、エミュレータが 2 つ動いていた。この条件で `test_ten_concurrent_moves_at_the_same_version_only_one_succeeds` が 1 回落ちた。単独で流すと、3 回とも通った。
  - 1b-2 でも、途中確認の回答の並行テストで同じ揺らぎが出たため、並行数を 5 本に減らしている。
- **見立て**: エミュレータの粗いロックの下で、再試行を使い切って、10 本とも 409 になる（1 本も通らない）ことがある。
  - 二重に効くわけではないので、安全性の問題ではない。
  - 「1 本は必ず通る」（先に進めること）が、エミュレータの負荷に左右される。
- **扱い**: ① の反証で扱う。

  - 本番の Firestore での振る舞いは、デプロイの後に確かめる。
- **追記（1d-2 の報告、2026-09-30）**: 頻度は想定より高い。
  - 素の HEAD でも、`test_answer_reevaluation.py`・`test_api_smoke.py` と一緒に流すと、5 回中 3 回、約 42 秒で落ちる。エミュレータのログは "Transaction lock timeout"。単独なら 6/6 通るが、3〜42 秒とばらつく。

### I-6（実装時の気づき / 設計 / low）デモ・攻撃の交渉の段の状態 `stages/{nid}` を消す経路がない

### I-7（実装時の気づき / 設計 / medium）本番で必須の設定（調査事項 R-2 の結果）と、R-1・R-3 の途中結果

- **R-2 の結果**
  - ADK は、既定でトレースにメッセージの内容を取り込む。本番では `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` が必須。対象は面談だけでなく、交渉エージェントも含む。

- **R-1 の結論**: ADK の `to_a2a` は使わず、受信口ごとの自前の AgentExecutor にした（1c）。`to_a2a` では、次のことが起きるため。
  - 検証違反が、A2A のエラーにならない。
  - セッションが、手番をまたいで残り得る。
  - TextPart も LLM に渡る。
  - `Move` が DataPart で返らない。
- **R-3 の途中結果**: pydantic の JSON Schema のままだと、google-genai が整数の列挙値を拒否する。
  - 数値軸は `type=INTEGER, format=enum, enum=[文字列]` に直した（1c）。
  - Vertex AI の実機で通るかは未確認。② の DV-15 で確かめる。

- **追記（1d-2 の報告、2026-09-30）**: デプロイの確認項目に、次を足す。
  - web は uvicorn を workers=1 で動かす。依頼者ごとのロック（I-4）は、プロセスの中の asyncio のロックなので、複数のプロセスでは保証が崩れる。
  - Firestore の TTL ポリシーを、web の `stages` の `ttl_at`（I-6）と、金庫のデモ・攻撃の交渉と、各イベントの記録の期限の項目に設定する。
  - web の必須の環境変数は `SESSION_SIGNING_KEY`（Secret Manager から渡す）と `VAULT_BASE_URL`。
  - サービス間の認証（Cloud Run の ID トークン）は、まだない。

### I-8（実装時の気づき / 設計 / low）金庫の冪等キーの文書 `idempotency/{hash}` が、依頼者の削除後も残る

- **根拠**: 1d-2 の報告。
  - 1b-1 は、交渉の作成の冪等（§3.5）のために `idempotency/{hash}` を置いた。中身は `nid` だけ。
  - web は、金庫に渡す `request_id` を `{pid}:{画面の値}` にしている（1d-2）。そのため、キーは依頼者 ID から作ったハッシュになる。
  - 依頼者の削除（§3.8）は、この文書を消さない。TTL もない。
- **破綻シナリオ**
  - 個人情報は含まないが、減ることがない。
  - 削除の後に、同じ依頼者 ID が同じ `request_id` で作り直すと、消えた交渉を指す文書に当たって 500 になり得る。画面が作る乱数なので、極めて稀。
- **扱いの案**: 冪等キーに TTL（例: 交渉の寿命 72 時間より長い 7 日）を付ける。または、依頼者の削除のときに消す。① の反証の場で決める。
- **反証 1 巡目の案**（reviews/round-9-correctness.md）: 7 日の TTL だけでは足りない（デモ・攻撃の交渉は 96 時間で消えるため）。次の 3 つを組み合わせる。
  1. 冪等キーはあるが交渉がないときは、古いキーとして上書きして作り直す。500 にしない。
  2. デモ・攻撃の冪等キーには、交渉と同じ `ttl_at` を付ける。
  3. 本人の削除で、交渉の文書の `request_id` から冪等キーを引いて消す。
