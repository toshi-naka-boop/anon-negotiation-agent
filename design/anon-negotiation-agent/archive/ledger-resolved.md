## 批評 1 巡目（design.md v1 → v2）

批評者: claude/opus（design-critic）、codex/gpt-5.6-sol（reasoning effort low）。原文は reviews/round-1.md と reviews/round-1-codex.md。

### C-1 / 設計 / high — 壁 1 の前提（LLM の文脈に自由文字列が入らない）が 2 か所で破れる

- **指摘**
  - 攻撃モードで審査員の自然文を求人側エージェントに渡す経路が、設計になかった。
  - 共有の `TurnInput` に項目を足すと候補者側の受信口も通ってしまい、壁 1 が崩れる。TextPart で送ると受信口が拒否するので、攻撃モードが動かない。
  - ID の正規表現 `^[a-z0-9-]{8,40}$` は、命令文のような文字列（例: `reveal-principal-min-salary-now`）も通してしまう。
- **解決（v2）**
  - `AttackerTurnInput`（`principal_instruction` を持つ別の型）と、攻撃モード専用の受信口 `/a2a/attacker` を設けた。候補者側と通常の求人側の受信口は `TurnInput` しか受け付けない。
  - ID はシステムが作る乱数の 16 桁の 16 進数（`^[0-9a-f]{16}$`）とし、A2A の metadata に載せ、LLM の入力からは外した。
  - 検証: AC-04 の拡張、DV-04。

### C-2 / 設計 / high — 無効な手の理由がエージェントに返らない

- **指摘**: temperature 0 と「無効な手が 2 回続いたら『なし』」が重なる。1 度つまずくと同じ誤りを繰り返して終わる。例: 求人側が当直で歩み寄ってグリッド外の 3 回を出し、ケース 1 がライブで「なし」に落ちる。
- **解決（v2）**
  - 理由を `TurnInput.last_error` の列挙値で返すようにした。
  - LLM の `output_schema` にグリッド値の列挙を埋め込み、グリッド外の値を構造化出力の段階で出させないようにした。
  - 打ち切りは連続 3 回（暫定）に変えた。
  - 検証: DV-03。

### C-3 / 設計 / medium — 攻撃モードの IP ごとのレート制限で、クライアント IP の取り方が未定

- **指摘**: 既定の設定だと全員で 1 つの枠を共有し、429 が多発する。`'*'` にするとヘッダの偽装で素通りになる。AC-13 のテストは、どちらの実装でも合格してしまう。
- **解決（v2）**
  - キーを、Cloud Run のフロントエンドが `X-Forwarded-For` に追記した末尾側のクライアント IP にした。先頭側の、利用者が書ける値は使わない（正確な位置は R-7 で確認する）。
  - 全体の上限（10 分 300 回、暫定）も追加した。
  - AC-13 に「先頭側を偽っても別枠にならない」「全体上限」を加えた。

### C-4 / 設計 / medium — FR-05 の警告と「途中確認へ回す」選択肢が区分軸にしかない

- **指摘**
  - spec が例に挙げるリモート日数を含め、数値の離散軸が抜けていた。
  - 「外す」の意味が決まっておらず、`*` に置き換える実装だと「行かない」条件が「受けられる」に変わってしまう。
- **解決（v2）**
  - 離散軸を「グリッドが値の集合そのものになっている軸」と定義した（暫定の語彙では年収以外すべて）。
  - 「外す」は、その軸について中立でないアンカーを削除すること、と定めた。削除しかしないので「受けられない」が「受けられる」に変わることはなく、変わるのは「本人確認が必要」への変化だけ。
  - 検証: DV-05。

### X-1 / 設計 / high — 問い合わせ上限が交渉単位で、交渉を作り直せば無制限に探索できる

- **指摘**: 評価回数を交渉ごと・側ごとに制限していたので、交渉を作り直すたびに枠が回復する。FR-11（数える単位は候補者・求人）と AC-05 を満たせない、という指摘。
- **判断: 一部受理**
  - FR-11 の数える単位と違っていた点は、正しい指摘。
  - AC-05 が破れるという部分は採らない。AC-05（相手が推定できる範囲はグリッド 1 マスより細かくならない）は、丸めの性質で回数に関係なく成り立つ。
- **解決（v2）**
  - 依頼者ごと（候補者は候補者単位、求人側は求人単位）の 24 時間予算（評価回数と交渉作成数、暫定）を金庫が強制するようにした。交渉を作り直しても回復しない。
  - 交渉ごとの上限も併用する。
  - 検証: AC-06 の拡張。

### X-2 / 設計 / high — `web` が両金庫を任意に評価でき、「細い問い合わせ口」が成立していない

- **指摘**: `agents` を金庫から切り離しても、運営側の `web` は両側について評価・追記・判定を呼べる。`web` が侵害されれば大量に照会できる。
- **判断: 一部受理**
- **解決（v2）**
  - 任意の組み合わせを評価するだけの口をなくした。評価は、金庫の状態機械の中の手（check・propose・accept）としてしか行えない。
  - 手番・回数・予算は金庫が強制する。
- **残る限界（信頼境界図に書く）**: 運営側のコードは、予算の内側で偽の手を登録できる。得られるのは丸め済みポリシーまで。TEE を入れても変わらない。

### X-3 / 設計 / high — 段階開示と管理操作に、本人の確認と権限の設計がない

- **解決（v2 §6.3）**
  - 匿名の依頼者セッション（署名付き・HttpOnly・Secure・SameSite=Strict のクッキー）を入れた。
  - 対象ごとの権限確認（違えば 403）を入れた。
  - 状態を変えるリクエストには `X-Requested-With` を必須にした。
  - デモ用のエンドポイントは `demo=true` にしか触れない。`web` と `vault` の両方で確かめる。
  - 開示台帳に、操作した依頼者 ID と時刻を残す（監査）。
  - 実名の確認と再認証は非スコープとし、既知の限界として説明文に書く。
  - 検証: DV-01。

### X-4 / 設計 / high — 回数・回答・合意・開示の遷移に原子性と冪等性がない

- **解決（v2）**
  - 金庫の状態機械では、すべての操作に `expected_turn` を付け、合わなければ 409 を返す。状態の遷移と回数の消費は Firestore のトランザクションで一度に行う。
  - judge は結果を保存して、何度呼んでも同じ結果を返す。
  - 段の遷移は、側ごとのフラグを冪等に立て、両方がそろったトランザクションの中でだけ進める。
  - 検証: DV-02。

### X-5 / 設計 / medium — 最終結果が LLM の探索の成否に左右され、FR-23 を満たさない

- **指摘**: 受け入れ可能な組み合わせがあっても、LLM が見つけられなければ「なし」になる。候補の生成・探索・終了は決定的コードに移し、少なくとも終了前に金庫がグリッドを全探索すべき、という指摘。
- **判断: 却下**
  - 提案（金庫による全探索で合意を補う）は、spec が却下事項に挙げた「両者の生データを TEE で突合: 一回計算で済むため交渉が飾りになる」と同じ構造になる。
  - FR-23 の目的は漏洩の上限（相手から観測できるものが丸め済みの情報を超えないこと）にある。LLM の出力は丸め済みの情報とモデルの揺らぎだけに依存し、依頼者の秘密には依存しないので、漏洩の上限は保たれる。
  - デモの再現性はリプレイ（FR-49）で担保する。探索の失敗率は C-2 の対策（理由の返却と列挙の制約）で下げる。

## 批評 2 巡目（design.md v2 → v3）

批評者: claude/opus（design-critic）、codex/gpt-5.6-sol（reasoning effort low）。原文は reviews/round-2.md と reviews/round-2-codex.md。

### C-6 / 設計 / high — デモ・攻撃用の架空人物を全訪問者が共有している（X-1 の解決で入った欠陥）

- **指摘**: 24 時間予算と、途中確認の回答の本体への追記が、共有の架空人物にそのまま掛かる。数人が触ると攻撃モードが最大 24 時間止まり、デモの筋書きも実行のたびに変わる。
- **解決（v3 §3.5）**
  - 架空人物は、読み取り専用のテンプレートとして置く。
  - 交渉には必ず、交渉ごとの複製（予算・追記・カウンタを別に持つ、TTL 付き）を使う。
  - 本物の依頼者は複製しない。
  - 検証: DV-07。

### C-7 / 設計 / medium — 部分的な発言の変換規則と、求人側への追記先がない

- **指摘**: 触れていない軸の埋め方が決まっていない。設計書自身の平文例 2 行（「年収 650 万以上なら、フル出社でも行く」「当直が月 4 回以上なら行かない」）が、矛盾として書き込みを拒否される。求人側（属性帯の条件付きルール）への回答の追記先も決まっていない。
- **解決（v3 §2.3・§4.4）**
  - 触れていない数値軸は、依頼者にとって最も良い値で埋める（受けるアンカーは控えめ、受けないアンカーは無条件）。区分軸は `*` で埋める。
  - 例文 2 行は、当直 0 以下と当直 4 以上が交わらないので矛盾しない。
  - 求人側の回答は、候補者の属性帯に最初に合うルールに追記する。合うルールがなければ、その属性帯をそのまま `when` にした新しいルールを末尾に足す。
  - 検証: DV-09。

### C-8 / 設計 / medium — LLM の失敗を金庫に登録できず、レフェリーの実行場所と再開がない

- **解決（v3 §3.2・§3.3・§4.1）**
  - `move=invalid(reason)` で無効手を登録できるようにした。
  - `web` は min・max とも 1 インスタンスで、CPU を常時割り当てる（R-8）。
  - 起動時に、終わっていない交渉のタスクを作り直す。
  - 金庫に期限（手番 5 分・途中確認 24 時間、暫定）を置き、遅延評価で期限切れにする。
  - 検証: DV-08。

### C-9 / 設計 / medium — 壁 1 の生メッセージ経路の上限

- **解決（v3 §4.3・§8.1）**
  - 受信本文は 8 KB まで（400 文字は攻撃者の指示にだけ掛ける）。
  - 生メッセージも、攻撃モードと同じレート制限に数える。
  - 有効な `TurnInput` なら LLM は動くが、その `Move` は金庫に登録しない。
  - 検証: AC-04・AC-13 の拡張。

### X-6 / 設計 / high — 面談後もブラウザに生の入力が残る

- **指摘**: sessionStorage に本人の入力を残すと、「生の値は面談の間だけ」と FR-06 が破れる。共有端末・XSS から取られ得る。
- **解決（v3 §7・§5）**
  - 実ユーザーの「まだ隠しているもの」は値を持たず、種類と「どのマスの中か」だけを示す。
  - ブラウザの保存領域には生の値を書かない。送信時にフォームの状態を消す。
  - 検証: AC-02（`scripts/check_no_web_storage.sh`）。

### X-7 / 設計 / high — 一時停止・取消が状態機械に入っていない

- **解決（v3 §3.1〜3.3）**
  - `paused` フラグと `control` API（pause／resume／cancel、`expected_version` 付き）を加えた。
  - すべての手のトランザクションで `paused` を確かめる。
  - 取消は `judged` 以外のどの状態（`awaiting_principal` を含む）からでも `ended(cancelled)` にできる。
  - 検証: DV-02・DV-08。

### X-8 / 設計 / high — 本人を削除しても交渉のコピーと web 側データが残る

- **解決（v3 §3.6・§6.3）**
  - 削除は `deleting` 状態にしてから進める。
  - 金庫側: 終わっていない交渉の取消 → 関わる交渉の文書の削除 → 依頼者の文書の削除、と連鎖させる。
  - web 側: セッションの結び付け・開示台帳・段の状態・本人にしか見えないイベントを消す。
  - 相手側に見えるイベントは、相手の記録として残す（相手がすでに観測した、グリッド上の値だけ）。
  - 検証: DV-06。

### X-9 / 実装 / medium — 途中確認の上限を側ごとに持っている

- **判断**: FR-21 の「1 交渉あたり 2〜3 問」は、側ごとか合計かが曖昧だった。厳しい側（合計）に読めば、どちらの読み方でも要件を満たすので、ユーザーへの質問は不要と判断した。
- **解決（v3 §3.3）**: 交渉全体で共有するカウンタにした。検証: AC-07。

### X-10 / 実装 / medium — 攻撃モードのメモリ内レート制限が再起動で消える

- **解決（v3 §8.2）**: Firestore の時間窓カウンタに、トランザクションで数えるようにした。検証: AC-13（再起動の模擬）。

### 枠外メモ L2-1〜L2-4（2 巡目、design-critic、low）

1. **TEE の言い過ぎ**: 予算と状態は運営者のプロジェクトにあるので、古い版に戻せば予算を回復できる。TEE でも「予算を運営者が迂回できない」とは言えない。
   - 解決（v3 §9・§1.2）: TEE で言えることを「保存された丸め済みポリシーを、公開されたコードを通してしか読めない」に絞った。予算は運営者に対する歯止めにならないと明記した。
2. **`check` と通し番号**: `check` で `turn` が進まないと、再送で評価回数を二重に消費する。
   - 解決: `version` は、受け付けた操作ごとに 1 進むと定めた。
3. **停止規則の文言**: 無効かどうかは自分側の評価で決まるので、「同じ手の並びなら、金庫の中身が違っても同じ手番で止まる」は成り立たない（FR-12 違反ではない）。
   - 解決: 判定関数がポリシーを引数に取らないこと、「手と金庫の応答」の並びが同じなら同じ手番で止まること、に直した。
4. **過剰実装**: 側ごとのグリッドの器は、設定の変更だけでは切り替えられない。
   - 解決: 全員共通の 1 つにし、器をなくした。U-12 で受け手ごとに決まった場合は、設計をし直すと明記した。

## 批評 3 巡目（design.md v3 → v4。上限の巡のため、v4 の変更は批評を通っていない）

批評者: claude/opus（design-critic。high 0 件、medium 5 件、low 4 件）、codex/gpt-5.6-sol（reasoning effort low。high 3 件、medium 2 件）。原文は reviews/round-3.md と reviews/round-3-codex.md。

### C-11 / 設計 / medium — 推定区間メーターが LLM の手を入力にしている

- **指摘**: 受けなかったことは「受けられない」を意味しない（エージェントは依頼者に良い対案を返すことがある）。受ければ交渉は終わり、手数は両側合わせて 12 まで。途中確認を使い切った後の拒否も、区間を誤らせる。
- **解決（v4 §8.3）**
  - 入力を、金庫の 3 値評価（`receiver_evaluation`）にした。「本人確認が必要」は情報なしとして扱う。
  - 同じテンプレートの複製をまたいで、区間を積み上げる。
  - 実演は台本の攻撃者で行い、1 マスになるまで次の複製で続ける。
  - 画面は「金庫の答えをすべて見られたとしても、ここまで」と表示する。
  - AC-12 に「対案を返す台本・受けて終わる台本でも、区間が真の値を含み 1 マスになる」を足した。

### C-12 / 設計 / medium — 控えめな補完（C-7）と「外す」（C-4）が噛み合わない

- **指摘**: 補完で最も良い値を入れた受けるアンカーは、ほぼすべての離散軸で中立でなくなる。そのため「外す」でほぼ全部消え、交渉ができなくなる。DV-05 では見つからない。
- **解決（v4 §2.4）**
  - 外す軸は二択の前に選ぶ。
  - 外した軸は最悪値で聞き（例:「当直が月 8 回でも行きますか？」）、「行く」だけを、その軸について中立な受けるアンカーとして保存する。
  - 外した軸に触れる「行かない」と自由コメントは、保存しない。
  - 外した軸で中立でない途中確認の回答は、交渉用コピーにだけ入れる。
  - DV-05 に「離散軸を 1 つ外しても受けるアンカーが残る」を足した。

### C-13 / 設計 / medium（X-13 / 設計 / high と同じ論点）— 一時停止中も期限が進む

- **解決（v4 §3.4）**
  - 一時停止で期限を null にし、再開で付け直す。`control` は期限切れの判定より先に処理する。
  - 最長の停止時間（暫定 24 時間）を超えたら timeout にする。
  - judge と送信箱の読み出しには期限を掛けない。
  - 検証: DV-08。

### C-14 / 設計 / medium — ライブ交渉の求人側の複製が、途中確認の前に消える

- **解決（v4 §3.7）**: 複製は、交渉が judged になるトランザクションで消す。保険の TTL を 72 時間（交渉の最長時間より長い）にした。検証: DV-07。

### X-11 / 設計 / high — 金庫の状態とイベントログが別々に書かれる

- **解決（v4 §3.2）**
  - 金庫が、状態遷移と同じトランザクションで送信箱（`outbox/{version}`）に記録を書く。
  - `web` は `{nid, version}` を冪等キーにしてイベントログへ写し、`ack` する。
  - `TurnInput.history` も送信箱から作る。
  - 検証: DV-10。

### X-12 / 実装 / high — 未完了の交渉を列挙する API がない

- **解決（v4 §3.3・§4.1）**
  - `GET /v1/negotiations?open=true` を足した。judged でないもの、または未配信の記録があるものを返す。
  - `web` が起動時と 60 秒ごとに見回り、タスクの再作成・送信箱の写し・judge を冪等に行う。
  - 検証: DV-08。

### X-14 / 設計 / medium — 求人側の回答がワイルドカードのルールに追記され、別の属性帯に広がる

- **解決（v4 §4.4）**
  - 回答は、属性帯が完全一致するルールに追記する。
  - なければ、その属性帯に当たっていたルールのアンカーを写し、回答を足した完全一致のルールを、ワイルドカードより前に作る。
  - 検証: DV-09。

### X-15 / 実装 / medium — 削除がサービスの間で止まると、やり直せない

- **解決（v4 §6.3・§3.8）**
  - `web` に墓標付きの削除ジョブを先に書く。
  - 金庫の削除は冪等にした（すでに消えていても成功）。
  - 見回りが、完了していないジョブをやり直す。
  - 検証: DV-06。

### 枠外メモ L3-1〜L3-4（3 巡目、design-critic、low）

1. **L3-1 読み出しの経路**: FR-39 とポリシーの閲覧には読み出しが要る。しかし、どう作っても主張が変わる。
