## 0. 結論

- **方向性には賛成。1on1 秘書案から乗り換えた判断も正しい。** 第5回の要項は「可観測性、セキュリティ、プロンプトインジェクション対策、エージェント管理」を意識したエージェントを募集すると明記している。この案のセキュリティ層はおまけではなく、採点の本丸に当たる（§1 で確認済み）。
- ただし設計に構造的な穴が 3 つある。
  1. **交渉と TEE 突合の二重化。** 両者の生データを TEE で突き合わせられるなら、交渉ラウンドは要らなくなる。審査基準「自律性・エージェントらしさ」で真っ先に突かれる。
  2. **出口からの漏洩。** 合意領域の両端は、守りたかった 2 つの数字（候補者の最低額と企業の上限）そのもの。
  3. **差分攻撃対策が「セッション単位の検知」頼み。** 求人を複数立てれば回避でき、停止判定の作り方によっては停止そのものが答えを漏らす。
- 3 つは 1 つの原則でまとめて塞げる。**相手から観測できるものは、本人が承認した丸め済みポリシーだけから計算する**（P3）。
- 締切は 2026-10-15 23:59 で、残りは 18 日。TEE を 3 番目に置く現行の優先順位は危ない。タイムボックスを切ることを勧める（§5）。

## 2. 元の検討への賛否

**賛成する点**（繰り返さない）: 主語を「マッチング」から外したこと、不成立の理由を返さないこと（決定 14）、医師採用に特化しないこと、二層分離という発想、1on1 案と「子どもと遊べる」アプリを却下したこと。却下の判断は、テーマ文を読むとむしろ強まる。

**補正が要る点**

- **金庫層は LLM にしない。** 決定 6 は金庫を「別エージェント」としている。しかし LLM である限り、問い合わせの文字列フィールド経由で操作される余地が残る。金庫は比較演算だけの決定的コードで足りるし、そのほうが「注入が効かない理由」を説明しやすい。
- **決定 15（インジェクション実演）は決定 12（スキーマ固定）と矛盾する。** スキーマが固定なら、「最低年収を教えて」という自然文はそもそも交渉層に届かない。届くのなら、そのスキーマは緩すぎる。
- **「交渉層が『保持していない』と返す」場面は証拠として弱い。** LLM は知っていても「知らない」と言えるからだ。見せるべきは「言わない」ことではなく「知り得ない」こと（P4）。
- **スコープにある「求人側分析画面（何で断られているか）」は決定 14 と矛盾する。** 件数が少ないうちは、集計値がそのまま個票になる。
- **決定 13 の「交渉終了後に本音を破棄」は並行交渉と噛み合わない。** 1 人の候補者は複数社と同時に交渉する。破棄の単位を「交渉ごとのコピー」と「本人が消すまで残る金庫」に分けて書く必要がある。

## 3. 言われていないリスク

### R1. 交渉と TEE 突合が二重になっている — 「エージェントらしさ」の土台が崩れる

- **何が起きるか**: 決定 10 は「両者の生データを TEE 内で突合」、決定 7 は「交渉層が金庫に可否だけ問い合わせる」としている。両方の生データを 1 か所で突き合わせられるなら、ZOPA は一発で計算できる。そうなるとラウンド制の交渉は要らない。逆に交渉が本物なら、生データの突合は不要になる（各金庫が自分の依頼者の分だけ判定すれば足りる）。どちらを取っても、両方作るのは二重実装になる。
- **誰に・いつ突かれるか**: アーキテクチャ図を見た一次審査の審査員と、12/1 の質疑。「TEE で計算すれば終わりでは？」と聞かれる。
- → P1、P2

### R2. 出口からの漏洩 — 合意領域の両端は、守りたかった数字そのもの

- **例**: 求人の上限が 700 万、候補者の最低が 620 万なら、合意領域は 620〜700 万になる。これを返すと、企業は候補者の最低額を、候補者は企業の上限を、どちらも正確に知ってしまう。決定 11 で入力は粗くしているのに、出力をどこまで粗くするかが設計されていない。
- 合意可能性スコアを連続値で出す場合も同じ。ラウンドごとに返すと勾配として使え、探索の手がかりになる。
- さらに合意領域は「会うか？」の承認より前に自動で出る。決定 5（承認なしに次の段を開かない）とも矛盾する。
- **誰に・いつ突かれるか**: セキュリティに明るい審査員。質疑で一言で刺されるタイプの穴。
- → P3

### R3. 本音を言う理由がない — 建前が 1 層内側に移るだけ

- 合意領域がその後の人間同士の交渉のアンカーになるなら、候補者は自分のエージェントに最低額を高めに申告し、企業は上限を低めに申告したほうが得をする。「本音ベース」という前提は、依頼者と自分のエージェントの間で崩れてしまう。
- 出力を「合意の見込み＋粗い帯」に絞れば、この歪みは大きく減る。高めに言えば会えたはずの相手を逃し、低めに言えば会っても決まらない面談が増える。だから正直に申告するのが一番得になる。帯を出す以上ゼロにはならないが、数値の合意領域を返すよりずっと小さい。R2 と同じ手で塞げる。
- **誰に・いつ突かれるか**: 交渉や HR に詳しい審査員と、事業化後の実ユーザー。
- → P3

### R4. 差分攻撃対策が「セッション単位の検知」になっている

- 年収 300〜1,500 万を 10 万刻みで持つと 121 通りある。Yes/No で答えるなら 7 問で特定できる（2^7 = 128）。セッションごとの回数制限は、求人を複数立てるだけで回避できる。架空求人を非スコープにしたことは、この穴を塞がないと宣言したのに等しい。
- 「レンジ帯で返す」は、帯が固定グリッドでないと効かない。問い合わせ値を中心にした帯（600±25 など）だと、少しずつずらして問い合わせた差分から境界が割れる。これがまさに差分攻撃そのもの。
- 停止判定が秘密値を参照すると（例:「真値に近づいたら止める」）、止まったこと自体が答えになってしまう。拒否や停止の判定は、過去の問い合わせと回答だけから行う必要がある（[Simulatable Auditing, PODS 2005](http://theory.stanford.edu/~kngk/papers/SimulatableAuditing.pdf)）。
- 最終結果の「合意あり/なし」も 1 ビット漏れる。上限を 10 万刻みに変えた求人を何本も立てれば、最終結果だけから最低額が割れる。
- **誰に・いつ突かれるか**: 「別アカウントで同じことをしたら？」と聞く審査員。事業化後は悪意ある求人側。
- → P3

### R5. 可観測性（テーマ）とプライバシーが衝突する

- テーマに合わせてトレースを入れた瞬間、面談の中身（本音）がトレースに残る可能性がある。ADK は LLM のリクエスト/レスポンスやツール引数をスパン属性（`gcp.vertex.agent.llm_request` など）に載せる実装を持っていて、`ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS` などで切り替える（既定値は言語とバージョンによるので要確認。[ADK Traces](https://adk.dev/observability/traces/)、[adk-python#4083](https://github.com/google/adk-python/issues/4083)）。これは決定 13（破棄）の抜け道になる。
- Gemini API の無料枠（Unpaid Services）では、入出力が製品改善に使われ、人手レビューの対象にもなり得ると規約に明記されている（[Gemini API Additional Terms](https://ai.google.dev/gemini-api/terms)）。本音を扱うアプリでは致命的なので、有料枠か Vertex AI を使う。Vertex AI（ドキュメント上は現在「Gemini Enterprise Agent Platform」表記）は既定で入力を最大 24 時間キャッシュする。キャッシュを無効化し、請求書払いでないアカウントは abuse monitoring 用のプロンプト記録について例外を申請すれば、ゼロデータ保持にできる（[データガバナンス](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance)）。
- **誰に・いつ突かれるか**: Google 側の審査員と、Zenn 記事の読者。
- → P6

### R6. Structured Output は受信側の防御にならない

- Gemini の Structured Output は「自分の出力」を整える機能にすぎない。相手が自前のエージェントなら（A2A なら誰でも接続できる）、任意の JSON を送ってこられる。本当の防御は受信側でのスキーマ検証で、自由文字列のフィールドが 1 つでも残っていれば、そこが注入経路になる。
- 金庫の「条件付き」回答も同じ問題を抱える。条件を自由に表現できると、選好の構造そのものが漏れる。
- → P5

### R7. 年収の定義がずれる（データの癖）

- 候補者は手取りや月給で考え、企業は額面や年収で考えがち。年収に固定残業代、賞与（何か月分を想定しているか）、手当が含まれているかもまちまちだ。医療なら当直・オンコール・外勤も絡む。正規化しないまま比べると金庫の判定がずれ、「会ってみたら全然違った」になる。信頼を失う一番の近道だ。
- **誰に・いつ突かれるか**: デモでは表に出ない。事業化後、最初のユーザーで表面化する。未決事項の「質問セット」と「判定スキーマ」に直結する。
- → P7

### R8. 身バレの最悪ケースは「現職の会社」

- 再識別で一番怖いのは、現職の会社が求人側として参加していて、自社社員の匿名プロフィールに気づくことだ。k 匿名性より先に、既存の転職サイトが備えている「企業ブロック」に相当する機能が要る。
- 「辞めた理由」は最も識別性の高いテキストになる。交渉が終わってから捨てるのでは遅い。制約に変換して本人が確認した時点で破棄する。
- 立ち上げ期は母数が少ないので、k 匿名性は原理的に成り立たない。設計書に「母数に応じて粒度を自動で粗くする」と書いておく。
- **誰に・いつ突かれるか**: 事業化後のユーザー、HR 領域に詳しい審査員の質疑。

### R9. 段階開示の順序が決まっていない

- 片側ずつ開示すると、先に開示した側が取られ損になる。相手は中身を見てから断れるからだ。
- → P8

### R10. 18 日で TEE を作るリスク

- Confidential Space は Confidential VM、Artifact Registry、Workload Identity Pool、KMS を組み合わせる構成になる（[概要](https://docs.cloud.google.com/confidential-computing/confidential-space/docs/confidential-space-overview)）。初めて触るなら構築に数日かかると見ておいたほうがいい（推測）。しかも現設計では、TEE の価値が一番薄い。R1 に加えて、面談の段階で運営側のバックエンドが生の本音に触れてしまうからだ。
- attestation を UI に出しても、リポジトリが非公開だと（要項上は非公開も可）イメージダイジェストとコードを紐付けられない。誰も検証できない「バッジ」で終わる。

## 4. 改善提案（MVP 優先）

### P1. アーキテクチャを 1 本にする — 金庫は TEE 内の決定的コード、交渉は TEE 外の LLM

- 金庫には LLM を置かない。面談エージェント（LLM）が本音を構造化ポリシーに変換し、本人が確認してから金庫に入れる。
- 交渉層（LLM）が持つのは、金庫への問い合わせ口（「この条件は受けられるか」）だけにする。
- TEE の役割を「両者の生データの突合」から、「問い合わせ口が細く絞られていることを、運営者でさえ迂回できないと証明すること」に変える。これで、attestation が何を証明しているのかを一言で言えるようになる。
- 両金庫を突き合わせる処理（最終判定）は TEE 内の 1 か所だけに置く。出力は P3 の粗い区分に限る。
- 面談の段階では、運営側のバックエンドが生の本音に触れる。これは図に正直に書く。言い過ぎないこと自体が、セキュリティの審査では信用につながる。
- TEE が間に合わなければ、金庫を Cloud Run 上の決定的コードとして出し、TEE 版は設計書に回す。二層分離の本質は「LLM に秘密を持たせない」ことで、TEE はその上乗せにすぎない。
- 金庫が決定的コードになるので、LLM を 2 体連携させるより実装は軽くなる。

### P2. 交渉が要る理由を言葉にする — 選好は事前に全部は言えない

- TEE で一発計算できない理由は、依頼者自身がすべての組み合わせについて事前に答えを持っていないことにある。交渉の価値は「言語化されていない選好を、必要になった瞬間に、必要な人にだけ聞く」ことに置く。
- **語彙は閉じて、組み合わせは開く。** メッセージの項目は列挙型（年収・リモート日数・入職日・研修・昇給見直しの時期・副業可否・当直回数など）と数値だけにし、自由文字列はゼロにする。LLM が担うのは、年収で詰まったら別の軸で組み合わせを探す、という戦略の部分だ。
- 事前のポリシーにない組み合わせが出てきたら、交渉の途中で依頼者に聞く。たとえば「年収 580 万・週 3 リモートは事前に聞いていない組み合わせです。受けますか？」。求人側も同じで、「経験 3 年だが、研修前提なら受け入れられるか」を採用担当に聞く。分からないときに人に聞く動きは自律性の見せ場になり、「人が握る」思想そのものでもある。
- デモの山場は「年収では届かなかったが、組み合わせで合意が見つかった」にする。年収レンジが重なるだけだと、「SQL の WHERE 句で済む」と見られてしまう。

### P3. 漏洩上限の原則 — 相手から観測できるものは、丸め済みポリシーだけから計算する

- 面談の最後に、本人が「最悪ここまでは知られてもいい粒度」を承認する（例: 年収は 50 万円単位）。金庫はポリシーを固定グリッドに丸める。判定・最終結果・停止など、相手から観測できるもの（厳密には応答時間も）はすべて、丸め済みのポリシーだけから計算する。
- こうすれば、問い合わせの回数、セッションの数、架空求人の本数に関係なく、相手が知り得るのは丸め済みポリシーまでになる。検知ではなく保証になるので、R2・R3・R4 が一度に塞がる。
- 出口は「合意の見込み（高/中/なし）＋承認済み粒度の帯」だけにし、数値の合意領域は返さない。高と中は、両者が受けられる組み合わせの広さ（1 点しかないのか、余裕があるのか）で分ける。交渉中は出さず、終了時に 1 回だけ出す。
- 検知や回数制限は残してもよい。ただし役割はコスト制御と早期警告に限る。数える単位はセッションではなく候補者にし、停止判定では秘密値を参照しない。
- UI では、本人に「最悪漏れてもここまで」を見せる。「まだ隠しているもの」パネルと対になる表示だ。
- トレードオフもある。丸めた分だけ、境界付近の案件を取りこぼしたり過大に評価したりする。誤差が「会ってから人が詰める」範囲に収まる粒度を選ぶ。

### P4. 攻撃の実演は「3 枚の壁」と「攻撃者の推定区間メーター」で見せる

- 壁 1: 受信側のスキーマ検証で弾く。自然文はそもそも届かない。
- 壁 2: 仮に届いても、交渉層の文脈には数字がない。交渉層のコンテキストを全文 UI に出して、「知らないと言う」のではなく「知り得ない」ことを見せる。
- 壁 3: 金庫は丸め済みのポリシーでしか答えない。
- 二分探索の実演は、「検知して止めた」よりも「攻撃者がどこまで推定できたか」を示すメーターのほうが伝わる。防御なしなら 7 手で「620 万」と特定される。防御ありなら「600〜650 万帯」から先に進めない。
- 余力があれば、デプロイ URL に「攻撃してみてください」モードを置く。審査員が求人側に自然文で攻撃を打ち込むと、それが構造化メッセージに変換され、帯でしか答えが返ってこない様子を見られる（審査員が実際に触るかどうかは分からない。推測）。

### P5. 受信側で守る

- 受信時に JSON Schema で検証する。自由文字列はゼロにし、列挙値と数値の範囲をチェックする。
- A2A を使うなら、TextPart は受信側で拒否し、DataPart だけを受け付ける。A2A を使う意味は、「相手が別ベンダーの自前エージェントでも安全」と言えることにある。

### P6. 可観測性は「値ではなく構造」を記録する

- トレースに出すのは「誰が・何回・どの項目を問い合わせ、どう答えたか（丸めた後の値）」まで。値そのものは出さない。面談と金庫の処理では、メッセージ内容のキャプチャを無効にする。
- 開示台帳と「まだ隠しているもの」パネルは、この可観測性を依頼者向けに見せるビューと位置付ける。依頼者が交渉を一時停止したり取り消したりできる画面を足せば、テーマの「エージェント管理」にもそのまま答えられる。
- 提出必須のアーキテクチャ図は、生の本音がどこに存在するかを色で示す信頼境界図にする。図そのものがセキュリティの説明になる。

### P7. 面談は「例示パッケージに行くか/断るか」で聞く

- 「最低年収は？」と聞かれると、本人も答えにくいし盛りたくなる。「A: 年収 580 万・週 3 リモート / B: 年収 650 万・フル出社、どちらに行きますか？」なら答えやすい。答えは金庫ポリシーの検証データにもなる（conjoint 分析と同じ考え方）。
- 年収の定義（額面か手取りか、固定残業代の有無、賞与の月数）は最初に正規化する（R7）。
- 抽出したポリシーは平文で本人に確認してもらう。HITL は出口だけでなく入口にも要る。

### P8. 段階開示は 3 段にし、双方が同時に開く

- 段 0（自動。本人が事前承認した粒度）: 合意の見込み＋帯
- 段 1（双方が「会う」を押した時点で同時に開く）: 企業名 / 候補者の匿名職務要約
- 段 2（双方が承認）: 氏名・連絡先。ここから人間同士の面談に移る

## 5. 実装優先順位の組み替え（決定 16 の置き換え案）

| 順 | 内容 | 狙う審査軸 | コスト感（推測） |
|---|---|---|---|
| 1 | 金庫（決定的コード）と交渉層（LLM）の分離、受信側スキーマ検証 | 実装品質、テーマ | 小 |
| 2 | 多次元パッケージ交渉と、途中で人に聞く動き | エージェントらしさ | 中 |
| 3 | 丸め済みポリシー原則と、3 枚の壁の攻撃デモ | テーマ（セキュリティ・注入対策） | 小〜中 |
| 4 | 出口（見込み 3 段階＋帯）と相互同時開示 | 新規性・有効性 | 小 |
| 5 | 値を出さないトレース、開示台帳、管理画面 | テーマ（可観測性・管理） | 小 |
| 6 | TEE に金庫を載せ、attestation を見せる（2 日でタイムボックス） | 実装品質 | 大 |

- **削るもの**: 求人側の分析画面（決定 14 と矛盾し、テーマにも効かない）。自由面談の作り込み（デモはプリセットの人物で進め、生の面談は 1 項目だけ見せる）。
- **TEE をやるなら**: 金庫のコンテナは公開リポジトリに置き、UI からイメージダイジェストとコミットの対応を辿れるようにする。
- **決定性を確保する**: デモ用のシナリオは temperature を固定し、リプレイモードを用意する。12/1 のライブで LLM が揺れても止まらないようにする。

## 6. 未決事項への叩き台

| 未決事項 | 叩き台 |
|---|---|
| 候補者への質問セット | 例示パッケージの二択を 5〜8 問、年収定義の正規化を 3 問。抽出結果は平文で本人に確認してもらう（P7） |
| 判定スキーマ・メッセージスキーマ | 列挙型と数値だけにし、自由文字列はゼロ。金庫の返答は「受けられる / 受けられない / 本人確認が必要」の 3 値。数値は返さない |
| 合意可能性スコア | 連続値は出さない。高/中/なしの 3 段階を終了時に 1 回だけ出す（P3） |
| 段階開示の段数 | 3 段、相互同時（P8） |
| ラウンド上限・回数制限 | 主役は丸め（P3）。回数制限はコスト制御として候補者単位で数える。デモの初期値は「1 交渉 10 問」「丸め 50 万円」あたりから（推測値なので要調整） |
| 属性の丸め粒度 | MVP は固定の粗い粒度と企業ブロック。k の保証は母数に依存するので、設計書に「母数に応じた自動粗粒度化」を書く |
| A2A を使うか | 使う。ADK の `to_a2a` / `RemoteA2aAgent` で低コストに載せられる（[ADK × A2A](https://adk.dev/a2a/)）。受信側は DataPart とスキーマ検証を通ったものだけ受け付ける（P5） |
| デモ用データ | 生成せず、3 ケースを手で設計する（組み合わせで合意する / 不成立で「不成立」だけが返る / 攻撃される）。背景の文章だけ LLM で肉付けする |
| LLM への本音送信 | 有料枠か Vertex AI を使い、キャッシュ無効化とトレースの内容キャプチャ無効化を行えば十分。金庫に LLM を置かない設計にすれば、TEE 内推論が必要かという論点自体が小さくなる |
| 「マッチング系はありがち」リスク | カテゴリを「マッチング」から「本音を預けられるエージェント」に移す。冒頭の一言の案:「人間の転職エージェントは『漏らしていない』ことを証明できない。このエージェントは証明できる。」 |
| 締切・提出物要件 | 裏取り済み（§1） |

## 7. 3 分デモ構成案

| 時間 | 場面 |
|---|---|
| 0:00–0:30 | 痛み: 求人票の上限に届かないと思って応募しない候補者と、実は出せるのに書けない求人側。「この 2 人は出会わない」 |
| 0:30–0:50 | 面談: 例示パッケージの二択に 2 問答える → 金庫ポリシーを本人が確認 → 「最悪ここまで知られる」粒度を承認 |
| 0:50–1:40 | 交渉: 左右に並べたログ。年収で詰まる → 組み合わせを探す → 途中で本人に 1 問 → 合意の見込み「高」 → 双方が「会う」 → 段 1 が同時に開く |
| 1:40–2:30 | 攻撃: 3 枚の壁で注入が構造的に届かない → 二分探索でも推定区間メーターが帯で止まる |
| 2:30–3:00 | 信頼: 信頼境界図と attestation（イメージダイジェストと公開コードの対応）→ 締めの一言 |

**ピッチの補強**

- **課題の定量化**: 公開調査で「条件が合わないと思って応募を見送った割合」を探したが、見当たらなかった（[マイナビ 転職活動実態調査 2026](https://career-research.mynavi.jp/reserch/20260924_114974/) を確認したが、該当する設問はない）。医師採用 5 年の実感を 1 つの数字にするのが一番強い（例: 条件次第で決まり得たのに応募されなかった案件の、体感での割合）。
- **先行研究**: Microsoft Research の Magentic Marketplace（2025）は、LLM エージェント同士の市場で、操作やプロンプトインジェクションに弱いこと、最初の提案に飛びつく偏りがあることを報告している（[論文](https://www.microsoft.com/en-us/research/publication/magentic-marketplace-an-open-source-environment-for-studying-agentic-markets/)）。構造的な防御が必要な根拠として 1 行で引用できる。
- **質疑用の 1 行**: 求人側が裁量を渡す理由は、「求人票に上限を書くと全応募者が上限を要求するが、候補者ごとに必要な分だけ開けるなら、書けない裁量を使える」から。
- 事業化について聞かれたら、職業紹介事業の許可が必要かを問われる可能性がある（推測。本業の方には自明と思うので一言だけ）。
