    - web と金庫の版がずれて、金庫が `MoveRequest` を 422 で断る（デプロイの途中など）。または、金庫の不具合で、ある手の登録だけが決まって 500 になる。

    - 止まるのは、見回りの `expire` が手番の期限（最後に手番が変わってから 5 分）で終わらせるとき。422 では金庫の手の処理に入らないので、手の側の期限切れの判定は効かない。

### 問題なしとした観点（最も危うい前提つき）

- 期限の付け直し（一時停止・再開・途中確認・寿命との組み合わせ）
  - 期限を書くのは、作成・手の後（手番か状態が変わったとき）・回答（一時停止中なら null）・一時停止（null）・再開（その時点から）・終了（null）だけ。どれも `expires_at` で頭打ちになる。手は一時停止中には通らないので、一時停止中に期限が付くことはない。
  - 一時停止中の回答 → 再開、の順でも、再開の時点から 5 分が付く。最長の停止時間と寿命は、付け直しの影響を受けない。
  - 最も危うい前提: check や無効手を重ねる手番は期限を付け直さないので、1 手番の中の LLM の呼び出しがすべて 5 分に入ること。台帳の「C-37 の残りのメモ」で既出なので、指摘にしない。
- 手数の数え方と停止の判定（DV-13・L9-3）
  - 有効な ask_principal は手数に数えないが、途中確認の上限（側ごとに 1）と評価の上限で回数が抑えられ、手番が進まないまま回り続けることはない。
  - 無効手で残りが尽きたときは同じトランザクションで 2 件、手番が戻ってきて残りが 0 のときは `end` の登録で手の前の停止の判定が効く。どちらも DV-13 の文言どおり。
  - 最も危うい前提: レフェリーが読んだ view の版と、`end` を登録するときの `expected_version` が同じであること。違えば 409 で読み直すので、別の状態で `end` が通ることはない。
- 冪等キー・削除のやり直し・外側の再試行
  - 作成のトランザクションは、キーと交渉の両方を読むので、古いキーの上書きと同時の作成は直列化される。負けた側はやり直しで、勝った側の交渉を返す。
  - 削除の手順 3 は、キー → 見え方 → 文書の消去（依頼者 ID は最後）の順。どこで止まっても、依頼者 ID が残っているので、やり直しで同じ交渉を引いて最後まで進む。キーを先に消しても、その間の作成は依頼者の削除中の確認で断られる。
  - 外側の再試行で呼び直す処理は、どれも外への作用を持たない（書き込みは txn に積むだけで、nid もやり直しごとに作り直す）。待ちは合計 0.6 秒以下。レフェリーの 60 秒はエージェントの呼び出しだけに掛かる上限で、金庫の呼び出しとは別の経路。金庫の呼び出しが web の時間切れ（30 秒）を超えても、`expected_version`・`request_id`・冪等な操作のため二重には効かない（エージェントを 1 回余計に呼ぶだけ）。
  - 最も危うい前提: 読み取りで出た `Aborted` は、内側の 5 回の再試行の対象外で、外側の 4 回しか再試行されない。本番の Firestore では 1 つの交渉への競合は小さいので、問題にしない。
- テストごとのプロジェクト ID
  - プロジェクト ID は関数スコープのフィクスチャ 1 つからだけ作られ、vault-db と (default) が同じ値を使う。ほかに Firestore のクライアントを作るのは本番の起動口だけで、テストでは差し替えている。モジュールやセッションのスコープで Firestore に触るフィクスチャはない。
