### 呼び出し側の補足（数えない GET・画面のページ・405）への判断

- **数えない GET の `/start`・入口の注記がクッキーつきで touch すること**: 是とは言えない。§8.2 の一般の規則（金庫か Firestore を読む要求を数える）と食い違う。`/start` の `session_start` の枠はルートの依存なので、touch の後に評価される（src/web/api.py:326-329）。単独の重さは 1 要求につき利用記録の読み出し 1 件（`/start` は枠のカウンタの読み出しも）で、それだけなら low。ただし同じ形の穴が POST に広く残っている（新しい欠陥 1）ので、そちらの直し方（touch の前に数える）でまとめてふさぐのがよい。`/start` は画面が面談の開始で 1 回呼ぶだけなので、表から外して数えても困らない（メモリの枠が Firestore の `session_start` の枠の前に立つ利点もある）。
- **画面のページを数える側にしたこと**: 正しい。ページはセッションの要る経路で、クッキーつきなら touch が走るので、§8.2 の一般の規則に当たる。ふつうの利用への影響は、画面のコードを動かして数えた（方法の (1)）。再取得に落ちたときの最も忙しい 1 分は、数えられる GET が /me 42・/demo 32・/attack 62 回。ページの HTML（1 回）と SSE の試み（1〜2 回）を足しても、1 画面で約 65 回まで、デモと攻撃を両方再取得で開いても約 100 回で、1 分 120 回に収まる。SSE がつながっていれば 1 画面 3〜27 回。当たるのは、3 画面を同時に再取得で動かすとき（約 144 回）・会場や職場の NAT・交渉の数がとても多い /me（low メモ 3・5）。副作用は、使い切った送信元ではページが 429 の JSON になること（low メモ 2）。
- **GET・POST 以外を 405 にしたこと**: 正しい。HEAD・PUT などのクッキーつきの要求は、読み取りの枠にも touch にも届かない（読み取りの枠は GET だけを見て、405 はクッキーの読み出し・touch・ロックより前）。画面とスクリプトは HEAD・OPTIONS を使わない（grep で確認）。ただし、同じ理由が POST にも当てはまることを見落としている（新しい欠陥 1）。`Allow` ヘッダが無い（low メモ 1）。

### 問題なしとした観点（根拠と、最も危うい前提）

- 本文の読み切り（X-90）と SSE・小さな POST・切断: 読み切った本文は 1 メッセージ（`more_body` は偽）で渡し、その後は元の receive に戻すので、切断の知らせ（sse-starlette の切断の見張り・長い処理の中の切断）は届く。読み取りの途中の切断は、応答を返さず、内側にも渡さない。期限は本文の全体に 1 つ（`asyncio.timeout`。Python 3.12）。小さな POST は、Content-Length あり・チャンク・Content-Length: 0 のどれでも通る（試験あり）。宣言を偽っても、HTTP の解析器が Content-Length を超える本文を渡さないので、数えた値で止まる。**最も危うい前提**は「本文のある要求は、必ず Content-Length か Transfer-Encoding を持つ」こと。HTTP/1.1 ではそうで（RFC 9112 の 6.3）、uvicorn は HTTP/1.1 だけを話し、Cloud Run のフロントエンドもコンテナへは HTTP/1.1 で渡す。web を h2c（`--use-http2`）で動かす形に変えると、宣言のない本文がこの判定を素通りする（いまの uvicorn では起きない）。
- 読み取りの枠の経路の選び方（C-72・C-73）: 突き合わせは、ルーターと同じ `compile_path` の正規表現を、ルーターと同じ `scope["path"]` に全体一致で当てる（`/health/`・`//health`・`/Health`・`/static` は数える。試験あり）。表の経路に当たっても、その先は固定の文・フィクスチャ・静的ファイル・attestation の口にしか届かない（`/static/../me` は StaticFiles が 404 を返し、セッションも素通り）。数えない GET の先が軽いことも確かめた（リプレイは 8〜15 KB のファイル）。**最も危うい前提**は「数えない表の経路は Firestore を読まない」ことで、クッキーつきの `/start`・入口の注記では崩れる（欠陥 1）。
- 決着の待ち（L21-1・L21-2）: 待ちは 8 回で必ず止まり、札（token）で古い交渉を読まない。操作（会う・承認）と選び直しは札を進めるので、待ちの鎖は 2 本にならない。**最も危うい前提**は「見回り 1 回の所要時間が 65 秒より十分短い」こと（125 秒から見回りの間隔 60 秒を引いた分）。進行中の交渉が数百件になると崩れる。
- deploy_check（X-88）: どの読めない形も NG に倒れ、`ORG_ID` を設定すれば祖先を読まずに組織の範囲で解析する。**最も危うい前提**は「組織の配下なら、`gcloud projects get-ancestors` の出力に organization の行が必ずある」こと（GCP ではフォルダは組織の中にしか作れないので成り立つ）。
- 405: 本文の上限の内側・読み取りの枠の内側・セッションの確認の前にあり、セッションの要らない経路にも効く。**最も危うい前提**は「Cloud Run の起動・生存の確認が GET である」こと（HTTP の probe は GET。手順書・deploy_check に HEAD・OPTIONS の利用は無い）。

### 試験が修正を確かめているか

- 壊せば落ちる形になっている: SSE の開始の 121 回目が、席・stages・金庫に届く前に 429（記録する偽物）。セッションのある GET の 121 回目が touch・金庫より前に 429。本番の app（TEE あり・なし）の GET の経路の全体の分類と、実際のミドルウェアの判断の一致。宣言なしの大きな本文が、セッション・ロック・ルート（本文を読まない `discard` も）より前に 413。遅い本文の 408（期限は全体に対して 1 つ）。本文のない要求を読まず待たないこと。X-88 の NG の各形と `ORG_ID` の道。決着の待ちの 125 秒と、失敗の後の読み直し・選び直しで止まること。429 の文。画面のコードを動かして GET を数える試験（L21-7 の改善）。
- 届いていないもの: `test_only_get_requests_are_counted`（tests/test_limits.py:974）は、POST を数えないことを、事実と違う理由（「POST は、それぞれの入口の枠が受け持つ」）で固定している（欠陥 1）。クッキーつきの `/start`・入口の注記が touch することは、どの試験も見ていない。405 の試験（1777 行）は、ミドルウェアを `__new__` で組み立てた単体で、本番の組み立ての順序の中では見ていない（読み取りの枠が HEAD を数えないことは `method == "GET"` の読みでしか確かめていない。害はない）。画面の試験の数え方の細部は low メモ 5。

### low のメモ（件数に数えない）

1. 405 に `Allow` ヘッダが無い（RFC 9110 の 15.5.6 は、405 に Allow を付けることを MUST としている）。あわせて、HEAD は静的ファイルでも 405 になった（v23 では StaticFiles が HEAD に 200 を返していた）。リポジトリの中に HEAD・OPTIONS を使う所は無いので、実害は見当たらない。`_reject` の 405 に `Allow: GET, POST` を足す。src/web/session_middleware.py:65-69・120-122。
2. 画面のページも数えるので、枠を使い切った送信元（会場の同じ Wi-Fi・職場の NAT）では、ページを開くと HTML の代わりに 429 の JSON がそのまま出る（v23 では、ページは開けて、画面の言葉で「画面の読み込みの回数が…」と出た）。発表の日に上げ忘れると、聴衆には壊れたページに見える。運用メモにこの症状を書くか、ページの経路の 429 だけ短い HTML にする。src/web/limits.py:569-585、src/web/app.py:97-103。
3. /me の読み込みでは、開示台帳が交渉ごとに活動ログを並行で読むので、交渉 N 件の依頼者は一度に N+5 回ほどの GET を出す（試験も「5 ＋ 交渉の数」を上限にしている）。評価予算で 1 日 10 件ほど作れ、最後に使ってから 30 日残るので、N が 110 を超える依頼者（予算を使い切って 11 日分）は、ページを開いただけで枠に当たり、SSE・段の読み込みまで 429 で止まる（再取得は 429 を一時的な失敗とみなさずに止める。static/ui.js:346-351）。今の使い方では起きにくい。終わった交渉の回答の読み込みを数件ずつにするか、遅らせる。static/ledger.js:96-128、static/me.js:285-301。
4. §6.2 の同じ段落に「期限切れで終わった交渉はフックが呼ばれないので、次の見回り（最大 60 秒）が決着させる」が残り、v24 で足した「期限切れにした次の見回りで決着するので、見回り 2 回分」と食い違う（実際は、期限から見回り 2 回分ほど）。design.md:803。
5. 画面が枠に収まることの試験（tests/test_ui_static.py:2716）は、ページの HTML の GET（1 回）を数えず、SSE のつなぎ直しを計算で足している（偽のサーバーが最終結果の後も一覧を active のまま返すので、決着の待ちの間の台帳の読み直しは多めに数える。こちらは安全側）。実測（方法の (1)）では、/attack の再取得の 1 分は 62 回＋ページ 1 回＋SSE の試み 2 回で約 65 回あり、運用メモの目安「見る人数 × 60」より少し多い（20 人で約 1,300 回）。3 画面（/me・/demo・/attack）を同時に再取得で動かすと約 144 回で枠に当たる（2 画面までは約 109 回で収まる）。目安を「× 70」にするか、試験にページの GET を足す。config/params.toml:283・309、design.md:919。
