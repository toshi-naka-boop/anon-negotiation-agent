### 指摘

- [C-52] 種別: 設計 / 深刻度: mid
  - 指摘: C-50 の直し「429・5xx が返った送信は計上を戻す」（§4.1・§8.2・DV-18）は、戻す対象を「Vertex AI が返した 429・5xx」に限ると書いていない。現行の信号は、agents の `_is_transient` が Vertex の 429・5xx と agents 側の時間切れ（`asyncio.timeout(llm_timeout_seconds=45)`）・httpx の TransportError を同じ `transient` 印で返し、web の client はそれらをすべて `ConnectionError` にまとめる。時間切れで切った要求は Vertex 側で完了して課金され得る（設計自身が「応答が失われても課金され得るため」としてレフェリーの再試行を計上している。§4.1）。印のまま戻すと「計上 ≥ 課金された要求」が崩れ、1 日の最悪の金額（§8.2）の根拠が消える。
  - 破綻シナリオ: 利用枠の 429 と重なって Vertex の応答が遅い日（② の 4 回目は最長 40 秒。I-13）、計画の呼び出しが 45 秒を超える。agents が時間切れで切る → `transient` 印の InternalError → client は `ConnectionError` → レフェリーは再試行（最大 3 回）。実装者が「transient ＝ 429・5xx」と読んで計上を戻すと、戻した分は Vertex で生成が終わって課金されている。1 論理呼び出しで最大 4 要求が課金され、計上は 1。1 日 1,500 の枠に対し課金は最大 4 倍。DV-18 の「429・5xx が返った分は戻る」を、`transient` を返すスタブで書くと、この誤った実装でも通る。
  - 提案: 戻す条件を「agents が、Vertex AI から受け取った HTTP 状態を A2A のエラーの `data` に明示して返した試行（例: `{"vertex_status": 429}`）」だけに限る。agents 側の時間切れ・httpx の TransportError・Cloud Run の 5xx・A2A の形の崩れでは戻さない（課金され得るので計上を残す）。§4.1・§8.2 に書き、§4.3 の応答の規則（`usage`）と同じ場所にエラー側の規則も書く。DV-18 に「agents の時間切れ（`transient` だが `vertex_status` なし）では戻らない」を足す。

- [C-53] 種別: 設計 / 深刻度: mid
  - 指摘: X-50 の直しで置いた `max_output_tokens`（2,048。§4.2）は、思考が長い呼び出しを「切れた JSON」にする。切れた JSON は agents の `json.loads` で ValueError → 印なしの失敗 → client は `ValueError` → レフェリーは再試行せず `schema_invalid` を登録する（L9-5 の経路）。`last_invalid` は 3 つとも null で手がかりがなく、temperature 0 でほぼ同じ入力に同じ長さの思考が返るので、3 回で `stopped_invalid` になる。費用の歯止めが「なし」を作る経路で、C-51 が消した「手がかりのない繰り返し」が別の形で戻る。DV-15 の「思考トークン数が `max_output_tokens` を超える呼び出しがない」は、上限が思考を含めて効くなら切られた呼び出しの `thoughts_token_count` も上限以下になるので構造上通り、切れたこと（finish_reason）を検出しない。
  - 破綻シナリオ: 計画の呼び出し（LOW）で、相手の案との差が大きい局面の思考が 1,900 トークンに伸びる（② の実測は MEDIUM で平均 820〜1,000。LOW の分布と最大は未実測で、§4.2 の「300〜800」は仮定）。出力 JSON（約 200）が入らず MAX_TOKENS で切れる → `schema_invalid`（手数 −1、連続無効 +1）、決定は呼ばない。次の手番の入力は `last_error=schema_invalid` だけが違う → 同じ思考 → 2 回目、3 回目 → `stopped_invalid` → 双方「なし」。DV-15 の 2 回（約 36 呼び出し）では分布の裾を見られず、デモの当日に初めて出る。
  - 提案: (1) agents は `finish_reason` を `usage` に載せ、MAX_TOKENS の呼び出しは「切れた」と分かる失敗（印 `truncated`）として返す。(2) レフェリーは切れた呼び出しを `schema_invalid` にせず、同じ手番で 1 回だけ、決定と同じ MINIMAL で呼び直す（物理の計上は 2 回。1 手番 2 回の上限を超えるので「切れたときだけ 3 回」と §4.1・DV-17 に書く）。呼び直しも切れたら `schema_invalid`。(3) 上限の値は、DV-15 で記録する `thoughts_token_count` の最大値の 2 倍以上（例: 4,096。1 日の最悪は約 $82 に増えるが有限）にし、DV-15 の判定を「`finish_reason` が MAX_TOKENS の呼び出しがない」に替える。

- [C-54] 種別: 設計 / 深刻度: mid
  - 指摘: X-50 の「クライアント側の自動再試行を切る（1 計上 ＝ 1 要求）」の確かめが、書かれた 2 つの形のどちらでも効かない。DV-17 の「スタブの BaseLlm が受けた要求の数が、レフェリーが数えた送信の数と一致する」は、自動再試行が住む `Gemini` モデル（`retry_options` → google-genai の tenacity）をスタブが置き換えるので、再試行が有効でも常に一致する。DV-15 の「200 応答の数は、agents 側が数えた Vertex AI への要求の数と一致する」は、agents の数に 429 の試行を含めれば 429 が 1 回出るだけで落ち（C-50 の再来）、含めなければ（成功時の `usage` の合計）自明に一致する。入っている版（ADK 2.10.0 は `Gemini.retry_options=None`、google-genai 2.25.0 の `retry_args(None)` は `stop_after_attempt(1)`）では今は切れているが、それを固定する検査がない（ADK の docstring は `HttpRetryOptions(attempts=2)` を例示しており、既定が変わり得る）。
  - 破綻シナリオ: ③-0 で DV-17・DV-15 が通る。後の版上げで ADK が既定の `retry_options` を持つか、デモ前に誰かが 429 対策として `attempts=3` を入れる。1 計上で最大 3 要求が Vertex に出る。交渉ごと 36・1 日 1,500 の計上に対し要求は最大 3 倍。どの検査も落ちず、§8.2 の最悪の金額が 3 倍になる。
  - 提案: (1) DV-15 の一致条件を「各 200 応答の `usage.requests`（agents が httpx のイベントフックで数えた、その A2A 呼び出しの中で Vertex に送った要求の数。429 の試行を含む）が 1 である」に替える。内部で 429 を再試行して成功すれば 2 になるので検出でき、レフェリーの再試行は別の A2A 呼び出しなので 429 で落ちない。(2) DV-17 に静的な検査を足す: agents が組み立てる `Gemini` の `retry_options is None`（または httpx の MockTransport に 429 を返させ、要求が 1 回で止まること）。

### 確認して問題なしとした観点

- C-47 の閉じ: 不変量「残り評価 ≥ 残り手数 ＋ 残り途中確認」が、すべての操作で保たれる。確かめは「>」の間だけ（等号で止まる）、`propose` は評価 −1・手数 −1、レフェリーが登録する無効手は手数 −1 だけ、`accept`・`reject` は手数 −1 だけ、有効な `ask_principal` は評価 −1・途中確認 −1、無効な `ask_principal`（`question_not_applicable`・`question_budget_exhausted`）は評価 −1・手数 −1。初期値 16 ≥ 6 ＋ 1。よってエージェントの手で `evaluation_budget_exhausted` は起きず、「受ける」の回答の後の `propose` にもガードの評価が残る。16/6/1 から数えると、途中確認を使わない筋は確かめ 9 回 ＋ 提案 6 回で評価 15、使う筋は確かめ 9 ＋ 途中確認 1 ＋ 提案 6 で 16（L14-1 の内訳）。
- C-48 の閉じ: 「本人確認が必要」が変わるのは自分側の `principal-answer` だけ。アンカーは足されるだけで矛盾は拒否され（§2.2・§4.4）、交渉用コピーは本体の PUT に影響されず、相手の回答は相手のコピーにしか入らない。回答の記録は答えた側の見え方にだけ入る（§3.2）ので、自分の `seq` で前後を判定できる。一時停止・再起動で回答がはさまらなければ埋まり、重ねて消費しない。
- X-51 の閉じ: `last_error`・`last_invalid` は最新の「エージェントの手」から作る。無効手は手番を変えないので、間に相手の手は入らず、入るのはレフェリーの確かめだけ。有効な手の後は null。DV-03・DV-17 の文と一致する。
- X-52 の閉じ: `stop_cost_limit` は `control`（`expected_version` なし、`judged` 以外のどの状態からでも）。§3.1 の `end_reason`（`stopped_cost`）、§3.3・§3.4・§4.1・§8.2・§14 が同じ語で揃っている。終了処理は共通なので最終記録は「なし」だけ（AC-08・FR-28）、コピーも消える（AC-17 の「上限での停止」に含まれる）。本人向け一覧は `judged` を `paused` より先に見る（`store.py` の `list_principal_negotiations`）ので、一時停止中に止めても「終了」と出る。
- X-53 の閉じ: 同じ `request_id` の再送は `stages` の対応を読んで入場の判定を通さない。二度押しが並行しても、金庫の冪等キーが同じ `nid` を返し、`stages/{nid}` への書き込みはマージで済む。起動時の 503 は見回りの読み終わりまで。
- C-50 の計上の不変量: 戻すのが「課金されない試行」に限られる限り、どの時点でも「計上 ≥ 課金された要求」が成り立つ（戻す前に落ちれば計上が多い側に残る）。崩れるのは C-52 の場合だけ。
- C-51 の閉じ: `checks` と `move` の両方は `checks` 優先。`schema_invalid` に残るのは「どちらもない」と `move=check`（構造化出力の列挙にないので LLM からは出ない）だけ。
- `usage` の経路: client は artifact の metadata を無視して DataPart だけを取るので、`usage` を載せても現行の受け手は壊れない（規則の明文化は L14-4）。壁 1・面談・交渉のどれも 1 日の数に入る。
- 節の整合: DV-15 の 1 コマンド（`--runs 2 --judge`）と §11 の ③-0 の完了条件が一致。§8.2 の 41 件 ＝ floor(1,500 ÷ 36)。基準値 820 の導き方（I-15 の $0.63 ÷ $9／100 万 ÷ 約 85 回 ≈ 823）は再現できる。§4.1 の図と本文（確かめは `moves check`、途中確認の後は `view` を読み直して計画）に食い違いはない。
