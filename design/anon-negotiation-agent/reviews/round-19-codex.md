### X-80（種別: 設計 / 重大度: medium）P-13 適用後も TEE の「実効権限」がオーナー込みになっている

- **どこが**: §9、§10(b)、契約 §16〜§18、`deploy_check.sh` は、KEK の実効主体を「オーナー＋active digest の principalSet」としています。一方、確定済み P-13 と §10(i) はオーナーを含む全主体を拒否し、WIF pool だけを例外にします。
- **破綻のシナリオ**: Policy Analyzer が allow binding を返すなら検査は通っても「実効権限」という主張が偽になります。deny を反映するならオーナーが結果から消え、期待集合との完全一致が失敗します。どちらでも TEE の主張と合格判定が一致しません。
- **直し方の案**: 「allow binding の集合＝オーナー＋digest」と「deny 適用後に実際に利用可能な集合＝active digest だけ」を分離してください。§9、§10、契約、期待値 JSON の説明を揃え、オーナーによる Encrypt/Decrypt が拒否される負の試験を追加します。

### X-81（種別: 実装 / 重大度: medium）公開された旧面談 API が必須の面談・確認を迂回できる

- **どこが**: §3.3b は段階的な面談 API だけを列挙していますが、実装は `POST /v1/principals/{pid}/interview` を意図的に残しています。任意の構造化アンカーと属性帯を直接受け取り、3 問・二択 5 組・確認・最悪ケース承認を経ずに金庫へ書きます。
- **破綻のシナリオ**: API 利用者は旧 API を一度呼ぶだけで登録済みとなり、交渉を開始できます。新しい面談フローのテストと AC-01 が通っても、公開面全体では「確認前の金庫書き込み 0」と必須面談が成立しません。
- **直し方の案**: 旧ルートを公開 router から外すのが最小です。互換性が必要なら、サーバ側に確認済み状態がある場合だけ受理するよう統合し、旧ルートによる直接送信を拒否するテストと API 一覧の完全性検査を追加してください。

### X-82（種別: 実装 / 重大度: medium）設計された二分探索の実演 API が存在しない

- **どこが**: §3.3b と §8.3 は `POST /v1/demo/attack/bisection` を公開 API としていますが、実装には当該ルートがありません。存在するのはメーター用の純粋な `simulate_bisection` とシミュレーション API だけです。AC-12 もこの HTTP 経路を検査しません。
- **破綻のシナリオ**: FR-45 の「ボタン一つで実交渉をまたいで探索する」デモが動かないまま、計算関数のテストだけで完了扱いになります。
- **直し方の案**: `attack_create` の制限下で、1 マスまたは交渉 3 件まで進め、交渉 ID 群と区間を返すルートを実装してください。OpenAPI、UI、HTTP 結合テストを AC-12/13 に加えます。

### X-83（種別: 実装 / 重大度: medium）本人用 SSE が開始後の削除状態を再確認しない

- **どこが**: `/v1/stream/` をミドルウェア外に置くこと自体は妥当ですが、本人用 SSE は接続開始時にだけクッキー、`deletion_state`、当事者性を確認します。その後の最大 30 秒間は金庫を直接読み続けます。
- **破綻のシナリオ**: SSE 接続後に本人削除が始まると、§6.3 の「削除中はすべての操作を拒否」に反し、金庫削除との競合中に新しい活動記録を送信し得ます。
- **直し方の案**: 各 poll の前に、長時間ロックを取らず `principals_meta` の存在と `deletion_state` を再確認し、削除中または削除済みなら即座に閉じてください。「接続後に deleting に変更したら次のイベントを送らない」試験も必要です。

### X-84（種別: 設計 / 重大度: low）GET による段の書き込みが POST 限定規則の例外になっている

- **どこが**: §6.2 は `GET .../stage` が `agreed_at`、架空求人のフラグ、台帳を冪等に書くと明記しますが、§6.3 は状態変更を POST と独自ヘッダに限定しています。
- **破綻のシナリオ**: SameSite=Lax のクッキーは外部サイトからのトップレベル GET に付くため、リンクを踏ませるだけで段の決着処理や台帳時刻を先行させられます。漏洩上限は広がりませんが、監査上の操作時系列と CSRF 方針が崩れます。
- **直し方の案**: GET を純粋な読み取りにし、決着処理を独自ヘッダ必須の POST に分けてください。GET 書き込みを維持するなら、この経路にも独自ヘッダを要求し、§6.3 に限定例外と安全性の根拠を明記します。
