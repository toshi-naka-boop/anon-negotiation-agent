### 台帳 I-5・I-8 への直し方の案

- I-5（DV-02 の揺らぎ）
  - 仕組み（推測。台帳の観測と合う）:
    - 2.32.0 のトランザクションは、コミットの `Aborted` を待たずに最大 `max_attempts` 回やり直す。本番では `retry_transaction` で順番を保つ前提になっている。
    - エミュレータでは、同じ文書を読んだ 10 本が、コミットで互いの共有ロックを待ち合う。時間切れ（"Transaction lock timeout"）で全員中止され、全員が同時にやり直す。
    - これを 20 回繰り返すと約 42 秒になり、台帳の「約 42 秒で落ちる」と合う。
  - テストの直し方: 性質を分け、どれも条件なしで確かめる。
    - 安全: 並行の結果は「通った数 ≦ 1」、失敗はすべて 409。
    - 何も消費しない、と前進: 並行の後に同じ要求を 1 本だけ逐次で送り直す。「並行で通った数 + 逐次で通った数 == 1」「version == 1」「評価の残り 15」「記録 1 件」を確かめる。
      - 並行で 1 本勝っていれば、逐次の送り直しは 409 になる。
      - エミュレータの負荷に関係なく、「1 回だけ効く」「失敗は何も消費しない」「詰まらない」が毎回確かめられる。
    - 「10 本のうち必ず 1 本通る」は、台帳の案どおり、デプロイ後の本番 Firestore の確認項目にする。
  - 補助:
    - 競合で再試行を使い切った 409 を、`MovePreconditionFailed` の子クラス（例: `ContentionExhausted`）にする。HTTP の 409 と detail はそのまま。テストとログで区別できる。
    - 任意: 金庫の `_run_transaction` を、内側 `max_attempts=5` × 外側 4 回にし、外側の間に 10〜200 ms の乱数待ちを入れる。エミュレータの一斉のやり直しを崩せ、本番の順番の保持は内側で保たれる。
- I-5（テストごとのデータ消去）
  - 原因の候補（推測）:
    - 後始末でタスクを cancel しても、止まらない呼び出しがある。金庫の同期ハンドラ（anyio のワーカースレッド）と、web の `asyncio.to_thread` の Firestore 呼び出し。
    - これらが次のテストの DELETE の後に書き込み得る（`tests/web_app_helpers.py` 9-12 行の注記が、この性質を認めている）。
    - `tests/conftest.py` 140-147 の DELETE は、応答を確かめない。
  - 案:
    - テストごとに一意のプロジェクト ID（例: `demo-test-{uuid}`）の Firestore クライアントを作る。エミュレータはプロジェクトごとにデータを分けるので、遅れて届く書き込みは古いプロジェクトに落ち、次のテストに混ざらない。消去そのものも要らなくなる。
    - 最低限なら、autouse の消去で、両方のデータベースに `raise_for_status()` と空の確認（`ensure_databases_are_empty` と同じ）を行う。
- I-8（冪等キー）
  - 「7 日の TTL」だけでは足りない:
    - デモ・攻撃の交渉は 96 時間で消える。96 時間〜7 日の間に同じ `request_id` が来ると、今と同じく 500 になる。
    - 500 になる箇所は `store.py` 258-263。`neg_snap.to_dict()` が None のまま `model_from_firestore` に渡る。
  - 案（3 つを組み合わせる）:
    - (1) 冪等キーはあるが交渉がないときは、古いキーとして上書きして作り直す（本物の依頼者なら、依頼者の文書がないので、その後の確認で断られる）。500 にしない。
    - (2) デモ・攻撃の冪等キーには、交渉と同じ `ttl_at` を書き、同じ TTL ポリシーを掛ける。
    - (3) 本人の削除の手順 3 で、相手が架空人物の交渉を消す前に、`idempotency/{sha256(doc.request_id)}` を消す。交渉の文書が `request_id` を持つので引ける（冪等）。
  - これで、冪等キーの寿命が交渉の寿命と揃う。§3.5 の「再送されても二重に作らない」は、交渉がある間はそのまま保たれる。

### 問題なしとした観点（最も危うい前提つき）

- version と seq:
  - 状態を変える経路は、すべて `_record_event` を通る。手・終了・無効手と終了の 2 件・停止の判定の終了・途中確認の回答・一時停止・再開・取消・期限切れ。
  - seq は、見え方を書く側だけ進む。
  - 前提: 新しい遷移を足すときも、この 1 か所を通すこと。
- 評価回数・手数・停止の数え方: §3.5 の表と一致する。
  - 評価: ガードの失敗・`question_not_applicable`・`question_budget_exhausted` も 1 消費する。受け手としての評価・確かめ直し・判定・評価し直しは数えない。
  - 手数: 有効な check 以外を数え、無効な check も数える。
  - 停止: 無効手で手数が尽きたときの即時終了は、手番が同じ側に残るので「回ってきた側の残りが 0」と同じ。
- 途中確認:
  - 追記先: コピーには常に書く。本体には、本物で、外した軸について中立なときだけ書く。
  - 評価し直し: 答えた側の `pending_offer` と `last_check` だけで、回数を消費しない。
  - 記録は、答えた側の見え方だけに入る。
  - 前提: `ask_principal` は「本人確認が必要」のときしか通らないので、コピーへの追記は矛盾しない。
- 削除と I-4:
  - 順序: web は、印 → 金庫 → 台帳 → 段 → 印の削除。各段は冪等で、失敗は依頼者の見回りがやり直す。
  - ロックの対象: ミドルウェア（要求の間）、削除の流れ（印の前から最後まで）、見回りの段の作成（ロックの後に金庫で確かめる）、レフェリー（金庫の呼び出しごと）。
  - 前提: web が 1 プロセス（I-7）。金庫の削除が web 側で時間切れになっても、金庫の deleting の印が、ロックの外の操作を止める。
- 利用記録とクッキー:
  - クッキーの期限は、書き込みと同じ時刻から 29 日。`delete_after` は 30 日。
  - 見回りは、`delete_after < now`（過ぎたもの）だけを拾う。印を立てる前に、`delete_after` が読んだ値から変わっていないことをトランザクションで確かめる。
  - DV-16 の境目のテストも、署名の中の期限で確かめている。
- 台帳の決定: 決定どおりに実装されている。
  - I-2: 帯は金庫が保存済みの値を読み、作成の要求では受け取らない。
  - I-3: 固定の窓。
  - I-4: 上のロック。
  - I-6: デモ・攻撃の段の状態に 96 時間の `ttl_at` を付け、本物には付けない。
