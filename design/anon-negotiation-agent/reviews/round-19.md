    4. 同時実行数だけを上げる直し（例 1,000）は別の所に効く。各ストリームは 2 秒ごとに `(default)`（`is_fictional_negotiation`）と金庫（`get_demo_events`）を読むので、1,000 本で金庫へ毎秒 500 件になり、TEE 版の金庫（n2d-standard-2 の 1 台）で、ライブ交渉のレフェリーの操作（手番 5 分の期限つき）と競合する。v20 は「1 回で金庫を最大 20 件読む」メーターに枠（60 回／10 分）を足したのに、30 秒で金庫を 15 回読む SSE は素通しになっている。
  - 提案:
    - §10 に `web` の containerConcurrency を明記し（例 250。asyncio なので SSE は軽い）、`deploy_check.sh` の `web-workers` で照合する。
    - SSE に、クライアント IP ごとの同時本数の上限（例 4）と全体の上限（例: containerConcurrency の半分）を置き、超えたら 429 を返して画面は 2 秒の再取得に落とす（再取得の GET にも IP ごとの枠）。全体の上限を同時実行数より小さくして、静的ファイル・リプレイ・面談の分を残す。

    - R-5 をこの数（同時本数・金庫への毎秒の読み出しの上限）で閉じる。

- [C-66] 種別: 設計 / 深刻度: medium
  - 指摘: v20 §5 の「面談の途中の状態は `web` のメモリ（… 同時 500 件まで）」は、500 件に達すると新しい面談を `503 too_many_interviews` で断る（`InterviewStateStore.create`）。一方、依頼者 ID を発行する `GET /start` と状態を作る `POST /v1/principals/{pid}/interview/begin` には、どの枠も掛かっていない（§8.2 の枠は、LLM を呼ぶか交渉を作る入口とメーターだけ）。共有の上限を、匿名のクライアント 1 つで埋められる。
  - 破綻シナリオ: クッキーを持たないクライアントが「`GET /start`（毎回新しい依頼者 ID の Set-Cookie）→ そのクッキーと任意の `X-Requested-With` で `POST .../interview/begin`」を 500 回繰り返す（計 1,000 要求。利用記録は作られず、Firestore への書き込みもない）。以後、本物の利用者の「面談を始める」はすべて 503 になり、面談を送れないので、ライブ交渉も作れない（本物の利用者の入口が全部止まる。デモは動く）。占有した状態は最後に使ってから 1 時間で読めなくなるが、50 分ごとに 500 個のクッキーで `GET .../interview/state` を呼べば延びるので、500 要求／時で占有を続けられる。`tests/test_interview_api.py` の上限の試験は「別のブラウザの `begin` が 503」を合格として固定している。
  - 提案: `begin`（新しく作るとき）に入口の枠を足す（例 `interview_begin`: IP ごと 10 分に 20 回。会場の Wi-Fi では同じ IP になるので、`interview_llm` と同じ考え方で値を決め、発表の日は上げる）。IP ごとに同時に持てる面談の数（例 20）も置き、全体の 500 は IP ごとの上限の後ろの最後の歯止めにする。上限に達したときの振る舞いと画面の文言を §5 に書く。アイドルの状態は見回り（60 秒）で消す（L19-6 も直る）。

### 確認して問題なしとした点（賛成の根拠と、最も危うい前提）

1. **公開の API（デモ・攻撃・メーター・デモの SSE）から本物の依頼者の交渉には届かない**（観点 (a)）。どの読み出しも、`web` の段の状態と金庫の `get_demo_events`（`mode` が demo・attack で、候補者が架空人物でなければ 404）の 2 段で確かめる。メーターは、存在しない ID も本物の ID も同じ 403。最も危うい前提は、壁 2（`walls/2/{nid}`）が `web` の段の状態だけで確かめている点だが、記録する側（`LlmContextRecorder.record`）が `mode == "live"` と依頼者 ID つきの交渉を受け付けないので、本物の交渉の文脈はメモリに入らない。
2. **SSE と静的ファイルをセッションのミドルウェアの外に置いても、本人の経路は開かない**（観点 (a)）。権限はミドルウェアではなく各ルートの依存（`require_session` など）で確かめるので、セッションのない要求は 401 になる。本人用の SSE は、クッキー・削除中・当事者を自前で確かめる（接続後の確かめ直しは X-83）。最も危うい前提は「セッションを見ない接頭辞（`/v1/demo/`・`/v1/stream/`・`/api/tee/`・`/static/`・`/health`）の下に、本人の経路を新しく置かない」ことで、置くなら自前の確認が要る。
3. **漏洩の上限（§2.5・§8.3）は保たれている**（観点 (c)）。活動ログは種類ごとに写す項目を限り（`activity_api._SHAPE`）、相手の評価・残り回数・`version`・終了理由は出ない。メーターは候補者側の `offer_received` と受け手としての評価だけを使い、グリッド上の値で区間を計算する。面談の生の値が `web` の外に出るのは Vertex AI への呼び出しだけで、v19 と同じ（面談の途中状態をメモリに置くことは、§1.2 の「生の値を扱う範囲」の中）。
4. **ブロック先を一覧から除かず作成で拒否する変更は、FR-13 を弱めない**（観点 (a)）。拒否は金庫の作成の中で、交渉もイベントも件数も生まれない（AC-16）。FR-13 が守るのは求人側から候補者が見えないことで、候補者本人に分かることは P-1 で受け入れた範囲と同じ（L19-5 は文面だけ）。
