### X-65（種別: 設計 / 重大度: high）TEE の「検証済み」が証明できる範囲を越えている

- **どこが**: §9 は「公開されたコードで動く」「鍵は指定ワークロードだけに渡る」とするが、AC-23 が確認するのは実行中のダイジェストと手動の L0 対応表まで。§10 も WIF の属性条件、KMS IAM、VM の SA に復号権限がないことを検査しない。
- **破綻のシナリオ**: 任意の作業ツリーを正規コミット名でビルドして対応表へ登録する、または広い KMS 権限を消し忘れる。attestation は合格するのに、公開ソースとの対応や鍵の排他性は成立しない。
- **直し方の案**: 「実行ダイジェスト」「ソース由来」「鍵の排他性」を別の保証段階にする。`deploy_check.sh` で WIF・KMS IAM を完全一致検査し、ソースの主張には署名付き Cloud Build provenance 等を必須にする。L0 の間は「許可リスト上のダイジェストが動く」までに弱める。

### X-66（種別: 設計 / 重大度: high）封印対象から候補者の属性帯と交渉関係が漏れている

- **どこが**: §3.1 の `participants` は候補者の属性帯を持つが、§9 の暗号化対象に `participants` がない。依頼者 ID・`job_id` などの関係情報も平文のままになる。
- **破綻のシナリオ**: Firestore の直接閲覧やエクスポートだけで、DEK なしに候補者の経験・地域・職種と、交渉した求人・企業の対応が読める。「Firestore の直接読みを封印が守る」という説明が実態より強くなる。
- **直し方の案**: 属性帯を `participants` から除去するか暗号化する。検索に必要な ID を残すなら、平文で漏れるメタデータを明記する。生の Firestore 文書へカナリアを入れ、指定した平文項目以外から見つからない検査を追加する。

### X-67（種別: 設計 / 重大度: medium）認証なし attestation の希少な発行枠を直列化していない

- **どこが**: 契約 §3 は `/v1/attestation` を認証なし・全体で毎秒 1 回にする一方、§8 の初回検証・再検証に single-flight の排他がない。公開側の `/api/tee/attestation` も同じ発行枠へ転送する。
- **破綻のシナリオ**: 起動時の見回りが複数要求を同時に出すと、一件以外が 429 になって金庫利用が失敗する。公開 API を継続的に呼ぶ利用者も、証明書更新時の内部再検証と競合して可用性を落とせる。
- **直し方の案**: 初回検証と付け替えを transport 単位の single-flight にし、待つ要求は同じ結果を共有する。公開 API は検証済み結果を基本的に返し、強制再発行には別の制限・キューを設ける。

### X-68（種別: 実装 / 重大度: medium）JSON モードへの切替が受入条件で固定されていない

- **どこが**: §2.7・§4.2・§4.3 は `application/json` のみで応答スキーマを渡さないとするが、DV-17 は `response_mime_type` と応答スキーマの不在を検査しない。
- **破綻のシナリオ**: ADK の `output_schema` が残る、または設定変換で応答スキーマが再び付いてもテストは通る。本番だけ制約付きデコードへ戻り、既知の 11〜55 秒の遅延で手番が落ちる。
- **直し方の案**: 計画・決定それぞれについて、生成された `LlmRequest` と偽 HTTP transport が受ける実ペイロードの双方で、JSON MIME があり、応答スキーマ関連フィールドがないことを検査する。

### X-69（種別: 設計 / 重大度: medium）`last_check` の意味が二重で、回答した組み合わせを保証する試験がない

- **どこが**: §2.7・§3.1 は `last_check` を「直前に確認した組み合わせ」と定義する一方、§4.4 は check ではない途中確認の回答 P で上書きする。DV-11 も、既存の別組み合わせ Q がある状態で `last_check.package == P` になることを要求していない。
- **破綻のシナリオ**: 実装が旧来どおり Q の評価だけを更新しても、Q の評価が回答と偶然一致すればテストを通る。次の `TurnInput` に P が現れず、エージェントが回答済みの提案を利用できない。
- **直し方の案**: `last_evaluation` へ改名して `source=check|principal_answer` を持たせるか、§4.4 の上書きを明示的な例外として全定義を揃える。Q≠P の状態から回答し、package・新評価・カウンタを検査するケースを DV-11 に加える。
