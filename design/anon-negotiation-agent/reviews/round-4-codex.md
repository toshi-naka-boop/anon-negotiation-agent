解決済み索引は除外し、v4 の追加策から新たに確認できる根拠があるものだけを挙げます。

1. 種別: 設計 / 重大度: high  
   一行タイトル: 1操作1レコードの outbox では、側ごとの可視性を表現できない  
   破綻シナリオ: [`outbox/{version}` を1件だけ書く設計](/Users/toshixa/dev/tenshokuagent/design/anon-negotiation-agent/design.md:278)なのに、提案パッケージは双方、自分側評価は自分だけ、受け手評価は受け手だけに見せる必要があります。同一レコードを `both` にすると相手側評価が漏れ、片側だけにすると他方の履歴・活動ログが欠落し、複数レコードにすると同じ `{version}` で衝突します。  
   直し方の方向: `{version, event_index}` ごとの複数イベントにするか、1操作の中に `candidate_projection` / `employer_projection` を持たせ、API側で必ず片側だけを射影する。ackもレコード単位または操作全体単位に明確化する。

2. 種別: 設計 / 重大度: high  
   一行タイトル: 期限到来だけでは終端遷移が起きず、無応答の交渉が永久に残る  
   破綻シナリオ: 期限切れ確認は [`moves` と `principal-answer` の冒頭だけ](/Users/toshixa/dev/tenshokuagent/design/anon-negotiation-agent/design.md:315)です。途中確認に誰も答えなければ、そのどちらも呼ばれません。60秒見回りもタスク再作成とjudgeしか行わないため、24時間を過ぎても `awaiting_principal`、snapshot、複製が残り、「なし」も配信されません。一時停止の最長時間も同様です。  
   直し方の方向: `expire-if-due` または期限超過一覧を処理する sweep API を追加し、見回りまたは Cloud Scheduler から呼ぶ。`version` と期限を比較するトランザクションで、通常の終了処理と同じ共通関数へ落とす。

3. 種別: 設計 / 重大度: high  
   一行タイトル: 複製の72時間TTLは、設計上の最大交渉時間より短い  
   破綻シナリオ: [`72時間は最大時間より長い`](/Users/toshixa/dev/tenshokuagent/design/anon-negotiation-agent/design.md:374)としていますが、途中確認2回×24時間＋停止24時間だけで72時間です。さらに12手×5分、LLM実行時間、見回り遅延が加わります。また停止時間は累積ではなく各pause単位なので、再開を挟めば繰り返せます。結果として進行中の複製がTTL削除され、次の回答・評価・judgeが失敗します。これはC-14への再提起ではなく、v4で置いた72時間という新しい根拠によるものです。  
   直し方の方向: activeな複製には固定TTLを掛けず、`judged` 後に `delete_after` を設定する。保険が必要なら状態遷移ごとにleaseを延長し、別途「交渉全体の累積絶対期限」を定義する。

4. 種別: 前提 / 重大度: medium  
   一行タイトル: 「生の値は面談中だけ」は、キャッシュ無効化だけでは成立しない  
   破綻シナリオ: 設計は生の値が面談後に残らないと断言していますが、R-3では abuse monitoring の例外取得を調査事項に置くだけで、リリース条件にしていません。Googleの現行仕様では、対象契約下で疑わしいプロンプトが最長90日保存される場合があり、キャッシュ無効化とは別にopt-out承認が必要です。[Google Cloud公式](https://cloud.google.com/vertex-ai/generative-ai/docs/learn/abuse-monitoring)  
   直し方の方向: キャッシュ無効の確認と abuse logging の免除・契約条件確認を、本物の入力を受け付けるための必須ゲートにする。確認できるまでは架空データ限定にするか、「自システムでは保存しない」という狭い主張へ信頼境界図と説明文を修正する。

5. 種別: 設計 / 重大度: medium  
   一行タイトル: 二重保存と削除サガが過剰で、削除時に終端イベントを消失させる  
   破綻シナリオ: 本人削除では、金庫が未終了交渉を取消して終端outboxを書いた直後、交渉文書とoutboxを削除します。一方、webへの転記は非同期見回りです。この順序では転記前に終端イベントが消え、相手側には交渉が終了した記録が届かず、web側の段状態も孤立します。`vault outbox → web複製 → ack → 削除ジョブ` は締切16日のMVPとしても重く、この競合を生んでいます。  
   直し方の方向: 「取消終端を書き、相手側投影の永続化をackしてから私的データを削除する」墓標付きサガにする。より小さくするなら、vaultの側別イベント列を唯一の正本にしてwebへの複製・ack自体をなくし、webは権限付きAPIから読む。
