### 問題なしとした観点（根拠）

- 決着処理の冪等性と並行: `record_agreement`・`settle_without_agreement`・`mark_settled`・`press` は、どれも 1 つのトランザクションで印を読んでから書くので、フックと見回りが同じ交渉を同時に決着させても、台帳の行と段の進みは 1 回だけ。`_auto_respond` は押すたびに返った状態で手元の状態を更新し、飛ばすのは「フラグが立っている」か「承認で段が 1 未満」のときだけなので、片方が途中で落ちても、印を立てた側がすべての手を済ませている。最も危うい前提は「作成時に `settled_at: null` を必ず書く」こと（`== None` の問い合わせは項目のない文書を拾わない）。作成は `_create_sync` の 1 か所だけで、ほかは `update` なので成り立ち、本番の `(default)` はこの変更の後に作られたので、項目のない古い文書もない。
- 削除との競合: `StageSettler.settle` は、本物の候補者の交渉を依頼者のロックの下で、利用記録が active のときだけ決着させる。フックはロックを持たない `run()` から呼ばれ（`PrincipalScopedVault` は 1 操作ごとのロック）、本人の POST は `StageFlow` を直接呼ぶので、二重取得もない。削除の後に段の状態や台帳を作り直さない（`tests/test_stages_settle.py:451`）。
- SSE の席: 権限の確認の前に取り、確認の失敗は `except BaseException` で、つないだ後は応答の `__call__` の `finally` で戻す（`SseSlot.release` は 1 回だけ戻す）。試験は、切断・problem・例外の 3 通りで席が 0 に戻ること、上限ちょうどと 1 本超えを本物の組み立てで見ている。X-83 の読み直しも各 poll の前にある。
- レート制限: `CLIENT_ONLY_ENTRANCES` は全体の文書を読まず書かない。HMAC の鍵は署名の鍵から固定のラベルで派生し、`RateLimiter` は鍵なしでは作れない（組み立ては `services.py` の 1 か所だけ）。
- 二分探索の実演: 交渉ごとに入口の枠と入場の制限を通し、作成の応答から `reserve` まで await を挟まないので、見回りが先に起こした本物のレフェリーがあっても、LLM に送る前に取り消される。残る窓は I-34 で記録済みのもの（失敗・時間切れの取消待ち）。ケース 3 の境目（600〜650）で、900 受・550 拒・700 受・600 拒・650 受の 3 交渉でちょうど 1 マスに届くことを手で追った（設計 §8.3 の「候補者が受けて終わる台本なら 3 交渉」と一致）。
- deploy_check: (b) のプール管理者は Policy Analyzer とプロジェクトの IAM の owner・pool admin の束縛の和で、空の結果と未完了の解析は NG。(h) は stop → start の後に launcher のログで既存の暗号文が開いたこと（`created the probe` でないこと）を見る。§10・AC-22 の v22 の文面と一致。
