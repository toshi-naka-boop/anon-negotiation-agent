    - 受ければ交渉が終わる。しかも手数は両側合わせて 12 までしかない。
  - 破綻シナリオ
    1. 審査員が攻撃モードで「年収を二分探索して」と指示する。
       - 攻撃者は、年収だけが決め手になる値に他の軸を固定し、900 万を提案する。

- [C-12] 種別: 設計 / 深刻度: medium — 受けるアンカーを控えめに補う規則（C-7）と「外す」（C-4）が噛み合わず、離散軸を 1 つ外すと受けるアンカーがほぼ全部消える
  - 指摘: 受けるアンカーのほぼすべてが、ほぼすべての離散軸について中立でなくなっている。そのため「外す」を選ぶと、受けるアンカーがほぼ全部消える。理由は次の 3 点。
    - §2.2 の定義では、受けるアンカーが軸 x について中立なのは、x が最も悪い値か `*` のときだけ。
    - v3 の §2.3 は、受けるアンカーの触れていない数値軸を、最も良い値で埋める。
    - 二択から作ったアンカーは、区分軸まで具体的な値で決まっている。

    - 手順 6 で、当直をどこまで受け入れるかを知られたくないので、`night_duty` を外す。
      - 残るのは当直が 8（最悪値）の受けるアンカーだけなので、7 件すべてが消える。

      - 候補者側エージェントの提案は、すべてガードで `not_acceptable_to_own_principal` になる。
      - 頼れるのは交渉全体で 2 問の途中確認だけなので、交渉はほとんど「なし」で終わる。
    - リモートと昇給見直しを外しても、同じことが起きる。触れていない軸が、最も良い値で埋まっているためである。
    - 区分軸（副業など）を外すと、二択から作ったアンカーがすべて消える。
    - DV-05（「受けられない」が「受けられる」に変わらないこと）は通るので、テストでは見つからない。
    - 画面には「次の組み合わせは途中確認になります」と出るが、その中身はほぼ全件になる。FR-05 の選択肢は、画面に出てはいても使えない。使えば交渉できなくなる。

    - 「外す」の判断を、二択（手順 3）より前に行う。
    - 外した軸は、二択の設問と自由コメントの変換で、中立の値に置く。
      - 受けるアンカーなら最悪値、受けないアンカーなら最良値、区分軸なら `*` にする。
      - 設問文にもその意味を書く（例:「当直が月 8 回でも、この条件なら行きますか？」）。
    - 二択の設問が問うていない区分軸は、既定で `*` にし、「どちらでも」と表示する。
    - 途中確認の回答のうち、外した軸について中立でないものは、交渉用コピーにだけ追記する。
      - 本体に入れると、次の交渉からは、外したはずの軸に金庫が答えてしまう。これは FR-05 と FR-22 の衝突になる。
    - DV-05 に次の合格基準を足す。「代表的な面談フィクスチャで離散軸を 1 つ外しても、受けるアンカーが 1 件以上残る」

- [C-13] 種別: 設計 / 深刻度: medium — 一時停止中も期限が進み、5 分を過ぎてから再開すると `timeout` で「なし」になる

- [C-14] 種別: 設計 / 深刻度: medium — ライブ交渉の求人側の複製が TTL 2 時間で消え、24 時間の途中確認が終わる前に相手の依頼者がいなくなる
  - 指摘: 次の 3 点が噛み合っていない。そのため、交渉の途中で、求人側の依頼者の文書（予算のカウンタと途中確認の追記先）が消えることがある。

    - 複製の TTL は、作ってから暫定 2 時間。一方で途中確認の期限は 24 時間。

  - 破綻シナリオ

      - 本人の回答は失われ、画面は待ち続ける。
  - 提案
    - 交渉の文書と、一時的な参加者（複製）の失効時刻を、交渉の期限に連動させる。

    - レフェリーが金庫から 404・5xx を受けたときの扱いを決める。
    - DV-08 に次の合格基準を足す。「複製の最初の TTL より長く途中確認を待っても、回答の後に交渉が続き、judge まで複製が残る」

問題なしと判断した点は、次のとおり。

- **丸めの性質（§2.4）**
  - 受けるアンカーは良い側へ、受けないアンカーは悪い側へ寄せるので、グリッド上の点では判定が変わらない。
  - 丸めは「受ける」と「受けない」の間を広げる向きにしか動かさないので、丸めによって新しい矛盾は生まれない。
  - AC-05 の上限は、問い合わせの回数に関係なく成り立つ。
- **「外す」の単調性（DV-05）**: 矛盾は書き込みの時点で拒否しているので、削除しかしなければ「受けられない」が「受けられる」に変わることはない。問題は単調性ではなく、残るアンカーの量にある（C-12）。
- **数の検算**
  - 全組み合わせは 25×6×5×2×2×2×3 = 18,000 通り。
  - 防御なしの 7 手は、300〜1500 万を 10 万刻みにした 121 通りに対して 2^7 = 128 ≥ 121 なので正しい。
- **過剰実装**: spec にたどれない大きな仕組みは見当たらなかった。「一覧の全件」と累計の読み出し口は、spec にない追加だが小さい。

### 枠外メモ（low・件数外）

- **L3-1 丸め済みポリシーを読む経路が API にない。足すと、§0 と §9 の主張が変わる**
  - FR-39 の「最悪漏れてもここまで」（§7「サーバ側の丸め済みポリシーから作る」）と、§6.3 の「ポリシーの閲覧」には、丸め済みポリシーを読む経路が要る。しかし §3.2 の API にはない。
  - 経路の作り方は 2 通りあり、どちらでも主張が崩れる。
    - `GET` の口を金庫に足すと、`web`（運営側のコード）が、どの依頼者の丸め済みポリシーでも読めるようになる。
    - `web` の DB に写しを持つと、§0 の「秘密を持つのは金庫だけ」が崩れる。
  - `web` のイベントログと開示台帳には、自分側の評価結果と途中確認の回答も、平文で残る（FR-37・38 のため）。
  - 最小の直し方
    - §3.2 に読み出しの口を足す。
    - §9 の「TEE でも言えないこと」に、次の 2 点を足す。
      - 本人に見せるための読み出しの口を通せば、運営側のコードは丸め済みポリシーを読める
      - イベントログと台帳は TEE の外にある
- **L3-2 レフェリーのタスクがないと、期限切れ・取消・停止で終わった交渉のコピーが TTL まで残る**
  - judge を呼ぶのはレフェリーだけで（§4.1）、コピーを消すのも judge（§3.2）。
  - タスクが例外で落ちたまま遅延評価で `timeout` になった交渉では、judge も最終イベントも起きない。
    - コピーが TTL まで残るので、FR-14 の「終了時に破棄」が満たせない。
    - 最終イベントが出ないので、FR-26 の「終了時に 1 回だけ出す」も満たせない。
  - 直し方
    - `agreed` 以外で `ended` にするトランザクションの中で、コピーを消し、`result = なし` を書く。
    - `web` は、`ended` を見たら最終イベントを出す。
- **L3-3 （TEE を実施する場合）Confidential Space では、Cloud Run の起動元 IAM が効かない**
  - §1.1 の「`vault` を呼べるのは `web` だけ」と、FR-15 をインフラ側で担保していることは、Cloud Run の起動元 IAM に頼っている。Confidential Space は Compute Engine の VM なので、この IAM が効かない。
  - そのため、§9 の「API は同じなので設計は変わらない」は正確でない。スパイクの 4 項目に、次の 2 点を足す必要がある。
    - `vault` が、`web` の ID トークンを自分で確かめること
    - VM へのネットワーク経路（VPC を経由し、外部 IP を持たせない）
  - 足さずに外部 IP で公開すると、ID を知っている人なら誰でも `moves`・`principal-answer`・`DELETE` を呼べてしまう。
- **L3-4 レート制限が、攻撃モードと壁 1 にしか掛かっていない**
  - デモ 3 ケースの実行とライブ交渉の作成には、IP ごとの上限も全体の上限もない。
  - 依頼者ごとの作成上限（1 日 20）は、次の理由で実質的に効かない。
    - ライブでは、匿名のクッキーを作り直せば回復する。
    - デモでは、毎回新しい複製を使うので、そもそも掛からない。
  - `web` は 1 インスタンスで、交渉ごとに非同期タスクを持つ（§4.1）。スクリプトでデモを連打されると、タスクと Gemini の呼び出しが積み上がる。同じインスタンスで動く発表者のデモも巻き込まれる。
  - §8.2 の Firestore の時間窓カウンタを、デモの実行と交渉の作成にも掛ければ済む。
