- [C-24] 種別: 設計 / 深刻度: low
  - 指摘: 依頼者のクッキーは `SameSite=Strict` で、「初回に ID を作る」（§6.3）。外部サイトのリンクから来た最初のリクエストには、このクッキーが付かない。それを「初回」と見なして新しい ID を作ると、元の ID のクッキーを上書きしてしまう。
  - 破綻シナリオ:
    1. 審査員が、提出ページのリンクからデプロイ URL を開き、面談とライブ交渉をする。
    2. 翌日、同じ提出ページ（または Zenn の記事）のリンクから開き直す。
       - サイトをまたぐトップレベルの遷移なので、ブラウザは Strict のクッキーを送らない。
       - 一方で、その応答で設定されたクッキーは保存する。
    3. `web` がクッキーのない要求を「初回」と見なして新しい ID を発行すると、元の ID は二度と使えない。元の依頼者には、次のどれも届かなくなる。
       - 活動ログ、開示台帳
       - 段の操作
       - 「データを消す」
    4. 本物の依頼者の文書には TTL がない。元のポリシーは金庫に残り続ける。FR-14 の「本人が消すまで残す」が、「本人が消せないまま残る」になる。
    - これが起きるのは、画面の読み込み（GET）で ID を発行する実装のときだけ。API の呼び出しで発行するなら、同じサイトからの要求になってクッキーが付くので、起きない。どちらにするかは、設計に書かれていない。そのため low とした。
  - 提案:
    - ID の発行は、明示的な POST（例:「面談を始める」）に限る、と書く。
    - あわせて `SameSite=Lax` にする。状態を変える要求は、POST と独自ヘッダに限っている（§6.3）。そのため、Lax にしても CSRF の守りは変わらない。

- [C-25] 種別: 設計 / 深刻度: low
  - 指摘: A2A のエラーとタイムアウトを、再試行せずにそのまま無効手として登録している（§4.1 の手順 4）。
    - そのため、Vertex AI の一時的な 429 や 5xx でも、同じ側で 3 回続けば `stopped_invalid` になり、「なし」で終わる。
    - モデル呼び出しを再試行するかどうかは、設計にも調査事項にも書かれていない。
  - 破綻シナリオ:
    1. デモケース 1 のライブ実行の途中で、Vertex AI が数秒間 429 を返す（共有の割り当ての混雑）。
    2. レフェリーは `invalid(agent_timeout)` を登録し、すぐ次の TurnInput を送る。同じ 429 がまた返る。
    3. 数秒で 3 回続き、交渉は「なし」で終わる。
       - 審査員には、ケース 1 が「合意できないシステム」に見える。
       - AC-09 のライブ実行も通らない。
    - 3 回に届かなくても、無効手は手数（12）を減らす。その分、合意に届く手が減る。
    - C-2 の解決は、「同じ誤りの繰り返しで、デモが『なし』に落ちる」のを防ぐためのものだった。基盤の一時的な障害を、エージェントの誤りと同じに数えると、その目的と逆になる。
  - 提案:
    - 429・5xx・タイムアウトは、手番の期限（5 分）の中で、指数バックオフで再試行する。無効手には数えない。
    - 交渉が必ず止まることは、手番の期限と寿命が保証する。
    - 無効手として数えるのは、スキーマ違反と、金庫が拒否した手だけにする。

### 件数外の low メモ

- **L5-1 `expire` が `agreed` にも効くかどうかが書かれていない**
  - 次の 3 つが揃うと、合意が期限切れに変わり得る。
    - §3.3 の `expire` は、「`expires_at` を過ぎていれば §3.1 の終了処理」と定める。
    - §3.1 の終了処理は、`agreed` 以外の終わり方のためのもの。
    - §4.1 の見回りは、`expire` を judge より先に書いている。
  - 寿命の間際に合意し、judge の前に `web` が再起動したとする。見回りが先に `expire` を呼び、合意を `timeout` の「なし」にする実装があり得る。DV-08 の「`agreed` の後に時間がたっても、judge は期限切れにならない」とも食い違う。
  - → 「`expire` は `active`・`awaiting_principal` だけを対象にする」と 1 行足す。
- **L5-2 一部の操作しか、見え方が決まっていない**
  - 決まっているのは、propose・一時停止・再開・最終結果だけ。
  - `check`、`ask_principal`、`invalid`、`accept`、`reject` の見え方は §3.2 にない。特に、金庫がガードで拒否した `propose(P)` の扱いがない。DV-10 も、propose しか確かめない。
  - 実装者が `ask_principal(P)` や `invalid(not_acceptable_to_own_principal)`（P を含む）を両側に見せたとする。相手は、その側の P の評価を知る。
    - グリッドの上限は破れない。
    - ただし、§3.2 の「相手側の評価は、どちらの見え方にも入らない」とは食い違う。
  - メーター（§8.3）は、攻撃者の訪問者に、候補者側の評価を見せる。そのため、DV-01 の「イベント列の読み出しは、本人の側としてしか呼ばれない」に、架空人物の例外を書いておく必要がある。
  - → 操作ごとの見え方を表にし、DV-10 をその表で確かめる。
- **L5-3 受信本文の上限 8 KB が、正当なメッセージの最大長に対して狭い**
  - 設計の項目どおりに、最も長くなる TurnInput を組んで長さを見積もった。
    - 見積もりの条件: 履歴 24 件（手 12・確認 10・回答 2）、7 軸の組み合わせ、JSON-RPC の封筒を含む。
    - TurnInput: 6.8〜7.5 KB
    - 400 文字の指示を足した AttackerTurnInput: 8.0〜9.9 KB
    - 幅があるのは、区分の値の表記（日本語か英字か）と、非 ASCII 文字をエスケープするかで変わるため。
  - 実際の交渉の多くはこれより短いので、たいていは通る。ただし、攻撃モードの終盤に長い指示を入れると、正当なメッセージが自分の上限で拒否され得る。その場合、無効手が続いて「なし」になる。
  - 上限の決め方に根拠がなく、最大長のテストもない。
  - → 上限は受信口ごとに、正当な最大長から決める（例: `/a2a/attacker` は 16 KB）。「最大長の正当なメッセージが通る」テストを、AC-04 に足す。
- **L5-4 `control` が `expected_version` を取るので、画面からの取消が 409 になりやすい**
  - 交渉中は、数秒ごとに version が進む。画面が持っている version は遅れがちなので、そのまま送ると 409 になる。
  - §4.1 は「画面の操作は、金庫の control にそのまま送る」と書くだけで、409 のときの扱いがない。
  - → 次のどちらかを書く。
    - `web` が送る直前に `view` で version を読み直し、409 なら数回やり直す。
    - 取消は `expire` と同じく、冪等な終端の操作にする。
- **L5-5 全体の上限は、発表者と聴衆で共有のまま（L4-2 への新しい根拠）**
  - v5 は、入口ごとに枠を分けた。しかし、全体の上限（10 分あたり 300 回）は全員で共有し、12/1 も「据え置く」としている（§8.2）。
  - ピッチで「攻撃してみてください」と誘えば、会場の聴衆が全体の上限を使い切り得る。そうなると、発表者のライブ実演も 429 になる。§14 の「発表者のデモが巻き込まれない」は、この点で成り立たない。
  - → 次のどちらかにする。
    - 発表者のセッションにだけ、別の枠を持たせる（設定で発行するトークンなど）。
    - §14 の主張を、「リプレイには逃げられる」に弱める。

### 4 巡目の解決の確認

| ID | 成り立つか | 根拠・最も危うい前提 |
|---|---|---|
| C-16 | 成り立つ | 評価し直した値は、元の評価・P・支配関係だけで決まる。受けるアンカー P を足したとき、評価が変わるのは P 以上の組み合わせだけで、エージェントにも計算できる。そのため、評価回数を消費しなくても新しい情報は出ない。また、「本人確認が必要」の P に回答を足しても、矛盾は起きない。受けないアンカー R と矛盾するのは P が R に含まれるときだけで、それは P が「受けられない」ことを意味するからである。最も危うい前提: 答えた側が、いつも `pending_offer` の受け手であること。質問できるのは手番の側だけで、`pending_offer` を出した側には手番がないので、成り立つ |
| C-17・X-17・X-18 | 成り立つ | 寿命は、一時停止では延びない。`expire` は冪等で、トランザクションの中で現在の期限と比べるので、直前に手が進んでいれば何もしない。複製の TTL（96 時間）は、寿命（72 時間）より長い。最も危うい前提: 見回りが動いていること（`web` が止まると、TTL だけが頼りになる）。`agreed` への `expire` は L5-1 |
| C-18 | 共有の問題は解けた | 同時に 1 件と、作成時の予約で、途中の予算切れと同じ質問の繰り返しはなくなった。ただし、解決で入れた仕組みが、C-22（AC-10 との衝突）と C-23（待ち行列）を持ち込んだ |
| C-19・X-16 | propose については成り立つ | 1 件の記録に側ごとの見え方を持つので、version が衝突しない。ほかの操作の見え方は L5-2 |
| C-20 | 成り立つ | 削った 3 つに依存している箇所は残っていない。金庫の `deleting` は削除の手順 1 のために必要で、削除ジョブがなくても意味を持つ。求人側の回答はコピーにだけ入り、DV-09 もそれを確かめる |
| X-19 | 成り立つ | §0・§1.2・§9・§14 の主張が、「このシステムは保存しない」に揃っている |
| X-20 | 写しとの競合はなくなった | 正本が 1 つになり、削除は自分側の見え方だけを消す。ただし、その正本に 96 時間の TTL が残った（C-21） |
| L4-1 | 成り立つ | §2.2 の定義では、区分軸の `*` は何も制約しない。「行く」を `*` で保存すれば、その軸について中立になる |
| L4-2 | 一部 | 入口ごとの枠は分かれた。全体の上限の共有は L5-5 |
| L4-3 | 成り立つ | 3 種類の表で、`judge`・`expire` と読み出しの扱いが決まった。副作用として、取消が 409 になりやすい（L5-4） |
